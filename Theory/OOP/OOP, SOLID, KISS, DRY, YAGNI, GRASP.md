 1) Наследование - позволяет создавать иерархию классов, вынося общие методы и свойства в родительский класс, а все наследники наследуют эти свойства и методы, а также могут переопределять их поведение и иметь собственные уникальные характеристики(open, override)

Можем создать метод, в котором аргументом будет родительский тип и сможем туда тогда прокидывать все дочерние типы. (Достигается за счет наследования, реализации интерфейсов и приведения типов)

 4) Абстрация - вынесение общих признаков в общий абстрактый класс игнорируя детали реализации(интерфейсы, абстрактные классы и методы)

Плохой дизайн
1. **Дизайн является жестким** (rigid), если его тяжело изменить, поскольку любое изменение влияет на слишком большое количество других частей системы.
2. **Дизайн является хрупким** (fragile), если при внесении изменений неожиданно ломаются другие части системы.
3. **Дизайн является неподвижным** (immobile), если код тяжело использовать повторно в другом приложении, поскольку его слишком сложно «выпутать» из текущего приложения.

### SOLID
 ##### Single Responsibility 
  - у каждого класса или метода должна быть единственная отвественность. Никаких god-object.
		Пример моей боли: 
			view-God Object
		Пример на работе: 
			я пришла в компанию Ingrad, и там было задание переписать плагин, потому что он был God Object
		Пример на работе: 
			когда команда уволилась, мне пришлось за 3х поддерживать приложения. И они были хорошо написаны, состояли из небольшиз файлов, с которыми было просто разобраться.
 
 ##### Open Closed - защита от шаловливых ручек.
 - сущности (классы, функции, модули) должны быть открыты для расширения и закрыты для модификации.
 Пример
 Мы создали класс, протестировали его и багов нет. Наш класс используют другие разработчики и все работает. Затем требования изменились и другие разработчики подкорректировали наш класс. И ВСЕ сломалось.

Пример из жизни: грамотную систему очень сложно создать и поддерживать, особенно когда нет постоянного ТЗ и постоянно меняются желания заказчика. И были ситуации, когда приходилось что-то менять и ломалось все. Да, регрессионные тесты должны быть и они подсветят. Но это не отменяет факта что нужно искать багу, откатывать и тд.
Нужно запретить изменять класс. Через private, через использование интерфейсов а не классов разработчиками и если действительно нужно поменять реализацию класса, то нужно создать свою реализацию на основе интерфейса и использовать ее.

Пример: есть класс string и мы ему можем добавить функцию расширения, которая будет делать что угодно, но при этом из функции расширения мы никак не можем изменить приватные и защищенные поля String
Мы можем отнаследоваться от класса string или создать композицию(добавить внутрь класса) и создать там свою функцию(менее красиво и предпочтительно) То есть за это отвечают open, фунции расширения - не надо тестить все опять, нужно только ваш код 

Пример: у нас есть репозиторий который работал с shared prefs. А мы теперь хотим работать с БД. Нам просто надо будет добавить реализацию для БД и через DI подставить ее в репозиторий.  И по сути протестировать просто нашу реализацию. Но я бы регрессию все равно запустила

### 🔥 **Принцип Open-Closed (OCP) в Android**

**Формулировка принципа OCP:**

> **Классы должны быть открыты для расширения, но закрыты для модификации.**

Это значит, что **мы должны уметь добавлять новую функциональность, не изменяя существующий код**.

---

## 🔴 **Нарушение OCP в Android**

Допустим, у нас есть `NotificationManager`, который отправляет уведомления:

```kotlin
class NotificationManager {
    fun sendNotification(type: String, message: String) {
        if (type == "EMAIL") {
            println("Отправка email: $message")
        } else if (type == "PUSH") {
            println("Отправка push-уведомления: $message")
        } else {
            throw IllegalArgumentException("Неизвестный тип уведомления")
        }
    }
}
```

### ❌ **Проблемы**:

- Если нужно добавить **новый тип уведомления** (например, SMS), придется **менять код** класса.
- Любое изменение **повышает риск ошибок** и требует тестирования всего класса.

---

## 🟢 **Соблюдение OCP в Android**

Вместо `if-else` мы используем **интерфейс**:

```kotlin
interface NotificationSender {
    fun send(message: String)
}

// Реализация для email
class EmailNotification : NotificationSender {
    override fun send(message: String) {
        println("Отправка email: $message")
    }
}

// Реализация для push-уведомлений
class PushNotification : NotificationSender {
    override fun send(message: String) {
        println("Отправка push-уведомления: $message")
    }
}

// Реализация для SMS
class SmsNotification : NotificationSender {
    override fun send(message: String) {
        println("Отправка SMS: $message")
    }
}

// NotificationManager теперь зависит от абстракции, а не от конкретных типов уведомлений
class NotificationManager(private val sender: NotificationSender) {
    fun sendNotification(message: String) {
        sender.send(message)
    }
}
```

Теперь легко добавить новый способ уведомлений **без изменения** `NotificationManager`:

```kotlin
fun main() {
    val emailNotification = NotificationManager(EmailNotification())
    emailNotification.sendNotification("Привет по Email!")

    val pushNotification = NotificationManager(PushNotification())
    pushNotification.sendNotification("Привет в Push!")

    val smsNotification = NotificationManager(SmsNotification())
    smsNotification.sendNotification("Привет по SMS!")
}
```

✅ **Теперь мы можем добавлять новые типы уведомлений, не изменяя существующий код!** 🚀

## 🎯 **Другие примеры OCP в Android**

### 📌 **1. View Binding и OCP**

Плохо:  
Если мы жестко привязываемся к `findViewById`, при изменении разметки код нужно **модифицировать**:

```kotlin
val button = findViewById<Button>(R.id.button)
button.setOnClickListener {
    println("Нажата кнопка")
}
```

Хорошо:  
С `ViewBinding` можно расширять функциональность без изменения кода:

```kotlin
val binding = ActivityMainBinding.inflate(layoutInflater)
binding.button.setOnClickListener {
    println("Нажата кнопка")
}
```

---

### 📌 **2. Adapter в RecyclerView**

Если `RecyclerView.Adapter` жестко привязан к одной модели, то при изменении нужно **переписывать код**.

Плохо:

```kotlin
class UserAdapter(private val users: List<User>) : RecyclerView.Adapter<UserAdapter.UserViewHolder>() {
    // ...
}
```

Хорошо:  
Используем **абстрактный адаптер**, который можно расширять:

```kotlin
abstract class BaseAdapter<T, VH : RecyclerView.ViewHolder>(private val items: List<T>) :
    RecyclerView.Adapter<VH>() {
    override fun getItemCount(): Int = items.size
}
```

Теперь можно **расширять адаптер, не меняя базовый код**:

```kotlin
class UserAdapter(users: List<User>) : BaseAdapter<User, UserAdapter.UserViewHolder>(users) {
    // ...
}
```

### 📌 **3. Dependency Injection (Dagger/Hilt)**

Вместо жестких зависимостей:

```kotlin
class Repository {
    fun getData() = "Данные"
}

class ViewModel {
    private val repository = Repository() // Зависимость жестко задана (плохо!)
}
```

Используем **внедрение зависимостей**:

```kotlin
class ViewModel @Inject constructor(private val repository: Repository) {
    fun fetchData() = repository.getData()
}
```

Теперь можно **менять реализацию `Repository`, не изменяя `ViewModel`**!

 ### 🔥 **Принцип подстановки Барбары Лисков (LSP) с примером "Прямоугольник и Квадрат"**

**Формулировка принципа LSP:**

> Если класс `B` является подклассом `A`, то объекты `A` могут быть заменены объектами `B` без изменения корректности программы.

Другими словами, **подкласс должен полностью соответствовать поведению родительского класса**, не нарушая его контракт.

---

### 🔴 **Нарушение принципа LSP: "Прямоугольник и Квадрат"**

Казалось бы, логично сделать `Square` (`Квадрат`) наследником `Rectangle` (`Прямоугольник`), но это ведёт к проблемам:

```kotlin
open class Rectangle(var width: Int, var height: Int) {
    open fun setWidth(w: Int) {
        width = w
    }

    open fun setHeight(h: Int) {
        height = h
    }

    fun getArea(): Int {
        return width * height
    }
}

class Square(size: Int) : Rectangle(size, size) {
    override fun setWidth(w: Int) {
        width = w
        height = w // У квадрата ширина всегда равна высоте
    }

    override fun setHeight(h: Int) {
        width = h
        height = h
    }
}
```

### ❌ **Проблема с этим кодом**

Если где-то в коде ожидают `Rectangle`, но получают `Square`, программа может работать **непредсказуемо**:

```kotlin
fun printArea(rect: Rectangle) {
    rect.setWidth(5)
    rect.setHeight(10)
    println("Площадь: ${rect.getArea()}") // Ожидаем 50
}

fun main() {
    val rect = Rectangle(2, 3)
    printArea(rect) // Выведет "Площадь: 50" (ОК)

    val square = Square(4)
    printArea(square) // Выведет "Площадь: 100" (НЕПРАВИЛЬНО!)
}
```

- Ожидаем, что площадь будет `5 * 10 = 50`, но у квадрата `width` и `height` всегда одинаковы, и мы получаем `100`.
- Код `printArea(rect: Rectangle)` начинает вести себя **непредсказуемо**.

### ✅ **Как исправить?**

Лучше **не наследовать `Square` от `Rectangle`**, а вынести их в **отдельные независимые классы** с общим интерфейсом:

```kotlin
interface Shape {
    fun getArea(): Int
}

class Rectangle(private var width: Int, private var height: Int) : Shape {
    fun setWidth(w: Int) {
        width = w
    }

    fun setHeight(h: Int) {
        height = h
    }

    override fun getArea(): Int {
        return width * height
    }
}

class Square(private var size: Int) : Shape {
    fun setSize(s: Int) {
        size = s
    }

    override fun getArea(): Int {
        return size * size
    }
}
```

Теперь метод `printArea` работает **корректно для любого Shape**:

```kotlin
fun printArea(shape: Shape) {
    println("Площадь: ${shape.getArea()}")
}

fun main() {
    val rect = Rectangle(5, 10)
    printArea(rect) // Площадь: 50

    val square = Square(5)
    printArea(square) // Площадь: 25
}
```

---

### 🎯 **Вывод**

- `Square` **не является** `Rectangle`, потому что у квадрата **поведение меняется**.
- Если `Square` наследует `Rectangle`, он **ломает ожидания**, нарушая LSP.
- Решение: **вынести общий интерфейс (`Shape`) и реализовать независимые классы**.

💡 **Moral of the story**: **Не пытайтесь наследовать классы только потому, что "они похожи" — подумайте, ведут ли они себя одинаково!** 🚀
 
 Interface sigrigation - принцип разделения интерфейсов. Нужно разделять интерфейсы на более мелкие, чтобы система не зависела от интерфейсов, которые ей нет смысла реализовывать. Нужно миллион раз подумать какие методы НЕОБХОДИМО добавлять в интерфейс и если их много, то лучше их выделить в отельные интерфейсы

 ##### Dependency Inversion
	 -  любую систему нужно строить так, чтобы она зависела не от реализаций, а от абстракций.
	  - Модули верхнего уровня (бизнес-логика) не должны зависеть от модулей нижнего уровня (детали реализации). Оба должны зависеть от абстракций.
	 - Абстракции не должны зависеть от деталей. Детали должны зависеть от абстракций.
 Принцип **инверсии зависимостей (Dependency Inversion Principle, DIP)** называется так, потому что он **"переворачивает"** традиционную зависимость в коде.
 Пример

### YAGNI
**YAGNI** (**«You aren't gonna need it»**; с [англ.](https://ru.wikipedia.org/wiki/%D0%90%D0%BD%D0%B3%D0%BB%D0%B8%D0%B9%D1%81%D0%BA%D0%B8%D0%B9_%D1%8F%D0%B7%D1%8B%D0%BA "Английский язык") — «Вам это не понадобится») — процесс и принцип проектирования [ПО](https://ru.wikipedia.org/wiki/%D0%9F%D1%80%D0%BE%D0%B3%D1%80%D0%B0%D0%BC%D0%BC%D0%BD%D0%BE%D0%B5_%D0%BE%D0%B1%D0%B5%D1%81%D0%BF%D0%B5%D1%87%D0%B5%D0%BD%D0%B8%D0%B5 "Программное обеспечение"), при котором в качестве основной цели и/или ценности декларируется отказ от избыточной функциональности, — то есть отказ добавления функциональности, в которой нет непосредственной надобности.

Многомодульная архитектура. Если приложение маленькое, не надо усложнять. Это не понадобится.
