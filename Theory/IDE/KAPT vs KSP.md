# KAPT vs KSP

Обе технологии решают одну задачу — **генерация кода по аннотациям** на этапе сборки. По ним живут Dagger/Hilt, Room, Moshi, Glide. Разница между ними — одна из главных причин, почему сборка Android-проекта занимает минуты, и частый вопрос про оптимизацию.

## KAPT — Kotlin Annotation Processing Tool
Обработчики аннотаций (`javax.annotation.processing`) написаны для **Java** и о Kotlin ничего не знают. Чтобы они заработали, KAPT делает обходной манёвр:

1. Компилирует Kotlin-код в **Java-стабы** — заглушки классов с сигнатурами, но без тел методов.
2. Скармливает эти стабы javac вместе с annotation processor'ами.
3. Собирает сгенерированный код и компилирует всё вместе.

Проблема в шаге 1: **генерация стабов идёт для всего кода модуля**, даже если аннотация встречается в одном классе. На больших модулях это половина времени сборки. Плюс KAPT ломает инкрементальность: изменил один файл — стабы пересобираются широко.

```kotlin
plugins { id("kotlin-kapt") }
dependencies { kapt("com.google.dagger:hilt-compiler:2.51") }
```

## KSP — Kotlin Symbol Processing
Разработан Google как замена. Процессор работает **напрямую с Kotlin-кодом** через API символов: видит классы, функции, свойства, nullability, extension-функции, `suspend` — то, чего в Java-модели просто нет.

Стабы не создаются вообще, javac в процессе не участвует. Отсюда результат: **сборка в среднем в 2 раза быстрее** (по замерам Google — до 2× на проектах с Room/Moshi), корректная инкрементальность.

```kotlin
plugins { id("com.google.devtools.ksp") }
dependencies { ksp("androidx.room:room-compiler:2.6.1") }
```
Миграция обычно сводится к замене `kapt(...)` на `ksp(...)` — при условии, что библиотека выпустила KSP-процессор.

## Сравнение
| | KAPT | KSP |
| --- | --- | --- |
| Как работает | Java-стабы + javac | напрямую по Kotlin-символам |
| Скорость | медленно (генерация стабов) | ~2× быстрее |
| Инкрементальная сборка | плохо | хорошо |
| Понимает Kotlin-специфику | нет (видит Java-проекцию) | да (nullability, suspend, extension) |
| Статус | **в режиме поддержки**, новые фичи не добавляют | рекомендованный путь |
| Поддержка библиотек | все старые процессоры | нужен KSP-совместимый процессор |

Кто уже поддерживает KSP: Room, Moshi, Hilt/Dagger, Glide, Koin (аннотации). Если библиотека KSP не умеет, остаётся KAPT — оба плагина могут сосуществовать в проекте.

## Compiler plugin — третий вариант
Есть ещё уровень ниже: **плагин компилятора**, который не генерирует отдельные файлы, а меняет код прямо при компиляции. Так работают `kotlin-parcelize`, `kotlinx-serialization`, Compose. Это быстрее любой обработки аннотаций, но писать такие плагины сложно, а их API нестабилен.

## Как ускорить сборку помимо KSP
- Разбить проект на **модули** — параллельная и инкрементальная сборка. См. [[Multi-module architecture]].
- `org.gradle.parallel=true`, `org.gradle.caching=true` в `gradle.properties`.
- Configuration cache и version catalogs. См. [[Gradle]], [[Dependencies via .toml]].
- Убрать неиспользуемые процессоры аннотаций — каждый стоит времени.
- Профилировать: `./gradlew assembleDebug --scan` покажет, куда ушло время.

## Вопросы-ловушки
- Почему KAPT медленный? → он генерирует Java-стабы для всего модуля и запускает javac, даже если аннотирован один класс.
- Что KSP умеет такого, чего не может KAPT? → видеть Kotlin-специфику: nullability, `suspend`, extension-функции, значения по умолчанию.
- Можно ли просто заменить kapt на ksp? → только если у библиотеки есть KSP-процессор; иначе оставляем KAPT, они уживаются вместе.
- Чем плагин компилятора отличается от KSP? → он модифицирует компиляцию напрямую, а не генерирует дополнительные исходники.
