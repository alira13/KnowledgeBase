Gradle — это система автоматизации сборки, используемая в Android Studio для управления зависимостями, сборкой и публикацией приложений. В Android Studio Gradle состоит из нескольких конфигурационных файлов, которые помогают управлять проектом и модулями.

Gradle делает процесс сборки гибким и настраиваемым, а также поддерживает автоматизацию, что упрощает сборку и развертывание приложения в различных конфигурациях.
### Как работает Gradle в Android Studio

Gradle выполняет сборку проекта поэтапно, разделяя процесс на задачи, каждая из которых выполняет отдельный шаг, такой как компиляция кода, сборка ресурсов, упаковка и обфускация. При запуске сборки Gradle обрабатывает зависимости, определённые в проекте, и выполняет задачи по порядку, основанному на их зависимостях.

Gradle также позволяет конфигурировать **Build Variants** — различные варианты сборки (например, отладочную и релизную), что полезно для создания APK с разными настройками.

### Основные файлы Gradle в Android Studio

1. **`build.gradle (Project)`**
    - Это конфигурационный файл для всего проекта. В нём задаются настройки уровня проекта:
        - **Gradle plugins** — добавление плагинов, таких как `com.android.application` или `com.android.library`.
        - **Classpath dependencies** — зависимости для сборки проекта. Например, здесь может быть указана версия плагина Android или Kotlin.
    - Пример:
```
// build.gradle (Project)
buildscript {
    repositories {
        google()
        mavenCentral()
    }
    dependencies {
        classpath "com.android.tools.build:gradle:8.0.2"
        classpath "org.jetbrains.kotlin:kotlin-gradle-plugin:1.5.31"
    }
}
allprojects {
    repositories {
        google()
        mavenCentral()
    }
}
```
2. **`build.gradle (Module)`**
    - Этот файл находится в каждом модуле проекта, например, в `app`, и определяет, как собирать конкретный модуль приложения.
    - Основные секции:
        - **android** — указывает конфигурации для Android-сборки:
            - `compileSdkVersion`, `minSdkVersion`, `targetSdkVersion` — версии SDK, используемые для сборки.
            - `buildTypes` — определяет, какие типы сборки существуют (например, `debug` и `release`).
            - `productFlavors` — позволяет создавать разные версии одного приложения, например, бесплатную и платную.
        - **dependencies** — зависимости, используемые в модуле, такие как библиотеки AndroidX или Retrofit.
    - Пример:
```
// build.gradle (Module: app)
plugins {
    id 'com.android.application'
    id 'kotlin-android'
}
android {
    compileSdkVersion 33
    defaultConfig {
        applicationId "com.example.myapp"
        minSdkVersion 21
        targetSdkVersion 33
        versionCode 1
        versionName "1.0"
    }
    buildTypes {
        release {
            minifyEnabled true
            proguardFiles getDefaultProguardFile('proguard-android-optimize.txt'), 'proguard-rules.pro'
        }
    }
}
dependencies {
    implementation "org.jetbrains.kotlin:kotlin-stdlib:1.5.31"
    implementation 'androidx.core:core-ktx:1.7.0'
}
```
        
3. **`settings.gradle`**
    - Этот файл указывает модули, входящие в проект. Если у вас есть несколько модулей, например, `app` и `library`, они будут перечислены здесь.
    - Пример:
	```
	// settings.gradle 
	include ':app'
	```
4. **`gradle.properties`**
    - Файл для настройки свойств Gradle. Позволяет установить глобальные параметры, такие как параметры кэширования или параметры компиляции, которые применяются ко всему проекту.
    - Пример:
```
    org.gradle.jvmargs=-Xmx2048m
	android.useAndroidX=true
	android.enableJetifier=true
```
5. **`gradle-wrapper.properties`**
    - Файл в папке `gradle/wrapper`, который указывает версию Gradle Wrapper. Wrapper позволяет запускать проект на определённой версии Gradle, не требуя установки Gradle локально.
    - Пример:
```
  # gradle-wrapper.properties
distributionUrl=https\://services.gradle.org/distributions/gradle-8.0-bin.zip
```
6. **`proguard-rules.pro`**
    - Файл, в котором указываются правила для ProGuard или R8, инструмента оптимизации и обфускации кода. Здесь можно задать, какие классы или пакеты не должны быть обфусцированы (например, чтобы сохранить работу с библиотеками).
**Обфускация кода** - это процесс приведения исходного кода программы к виду, сохраняющему исходную функциональность, но затрудняющему анализ, понимание алгоритмов работы и модификацию при декомпиляции. Этот процесс используется в случаях, когда исходный код программы содержит конфиденциальную информацию, а также злоумышленниками, которые хотят скрыть свои злонамеренные действия от антивирусных программ.

### Этапы сборки проекта Gradle

1. **Инициализация (`Initialization Phase`)**
    - На этом этапе Gradle определяет, какие проекты и модули будут участвовать в сборке. Этот процесс начинается с обработки файла `settings.gradle`, в котором перечислены все модули (например, `app`, `library` и т. д.).
    - Gradle создает **граф проектов** — дерево всех модулей проекта, каждый из которых может быть связан зависимостями.
2. **Конфигурация (`Configuration Phase`)**
    - На этапе конфигурации Gradle загружает все `build.gradle` файлы для каждого модуля и анализирует зависимости, указанные в них. Конфигурационные скрипты выполняются, и формируется граф задач для каждого модуля.
    - В этом графе задач Gradle определяет зависимости между задачами, чтобы понять, в каком порядке их выполнять. Например, задачи по компиляции ресурсов должны выполняться до компиляции кода.
    - Здесь же Gradle определяет, какие варианты сборки (например, `debug`, `release`) и флейворы будут собраны на основании конфигураций `buildTypes` и `productFlavors`
3. **Выполнение задач (`Execution Phase`)**
    - Этот этап выполняется в несколько подэтапов и состоит из выполнения задач для каждого этапа сборки. Каждая задача отвечает за конкретный процесс, например, компиляцию кода или упаковку ресурсов. Основные задачи:
        - **Компиляция ресурсов:** задачи `mergeResources` и `processResources` собирают ресурсы (изображения, XML-файлы и т.д.) и подготавливают их для включения в APK.
        - **Компиляция кода:** Gradle запускает `compileJava` (для Java) или `compileKotlin` (для Kotlin), чтобы скомпилировать исходный код в байт-код. Также на этом этапе происходит анотация, инъекция зависимостей и другая предкомпиляционная обработка.
        - **Линковка кода и ресурсов (`Linking`):** происходит связывание ресурсов и кода, а также генерация окончательных файлов `R.java` или `R.kt`, которые содержат идентификаторы ресурсов.
        - **Оптимизация и обфускация кода:** если выполняется `release` сборка, включается задача по оптимизации (например, ProGuard или R8), которая уменьшает и обфусцирует код, удаляя неиспользуемые классы и функции, уменьшая размер APK и затрудняя реверс-инжиниринг.
        - **Упаковка (Packaging):** с помощью задачи `package` создается APK или AAB-файл. Файлы кода, ресурсов и манифестов объединяются в единый исполняемый файл.
        - **Подписание (Signing):** при релизной сборке выполняется подпись APK. Если APK подписан, он может быть загружен в Google Play и использоваться на устройствах.
        - **Создание итогового артефакта:** на заключительном этапе Gradle завершает сборку, создает итоговый файл, и помещает его в папку `build/outputs/`, где APK или AAB становится доступным для тестирования или развертывания.
4. **Публикация и тестирование**
    - Если проект настроен на публикацию, на этом этапе выполняется задача загрузки артефакта в Google Play или другое хранилище.
    - Gradle также поддерживает автоматизацию тестирования: на этапе конфигурации и выполнения могут быть вызваны задачи тестирования, такие как `test` (для юнит-тестов) и `connectedAndroidTest` (для инструментальных тестов, которые работают на реальном устройстве или эмуляторе).

**Gradle** — это инструмент автоматической сборки приложений, который помогает получить собранный проект из исходных файлов с кодом и ресурсами.

- Папка gradle содержит утилиту gradle-wrapper, которая помогает установить Gradle для проекта.
- Файлы gradlew и gradlew.bat представляют скрипты для выполнения команд от Gradle на компьютерах с Linux и Windows.
- gradle.properties — это файл настроек, в котором устанавливаются значения свойств Gradle.
- settings.gradle — это конфигурационный файл проекта, в котором указываются модули, нужные в проекте.
- build.gradle — файл в котором прописан сценарий сборки. Подробнее про Gradle мы поговорим в следующих темах.
    
- В папке .idea находятся конфигурационные файлы проекта Android Studio, которые нужны в процессе работы с проектом.
- C файлом .gitignore мы знакомились в предыдущих уроках. Напомним, он нужен, чтобы система контроля версий могла понять, какие файлы не подлежат версионированию.
- Последний файл local.properties содержит настройки системы, например, путь до SDK. Сразу скажем, что в работе мы взаимодействуем не со всеми файлами и директориями. Некоторые из них нужны среде разработки или системе сборки, например, .gitignore, .idea и .gradle.

В Android (и на Kotlin, и на Java) `minSdkVersion` и `targetSdkVersion` — это параметры, которые указываются в `build.gradle` (или `build.gradle.kts`, если ты используешь Kotlin DSL). Вот краткое объяснение:

---

### 📌 Что такое `minSdkVersion`?

- Это минимальная версия Android (API level), на которой **приложение может запускаться**.
    
- Если устройство пользователя использует версию Android ниже этой — приложение **не установится**.
    

---

### 📌 Что такое `targetSdkVersion`?

- Это версия Android, **на которую ты ориентируешься при разработке**.
    
- Говорит системе: "Я знаю об особенностях этой версии, и мое приложение работает с ними правильно".
    
- Если версия Android выше, чем `targetSdkVersion`, могут быть включены **режимы совместимости**, чтобы старое поведение сохранялось.
    

---

### Пример (в `build.gradle.kts`):

```kotlin
android {
    compileSdk = 34

    defaultConfig {
        applicationId = "com.example.myapp"
        minSdk = 21           // Минимальная версия Android (например, Android 5.0)
        targetSdk = 34        // Целевая версия (например, Android 14)
        versionCode = 1
        versionName = "1.0"
    }
}
```

---

### 🔍 Как выбрать `minSdk` и `targetSdk`?

- **`minSdk`** зависит от того, какую аудиторию ты хочешь охватить. Например, `21` (Android 5.0) покрывает более 90% устройств.
    
- **`targetSdk`** всегда стоит ставить на **самую последнюю стабильную версию** — это помогает пройти проверку Google Play и получать новые фичи/поведение.

Совместимость между версиями Java и Kotlin — важный аспект при разработке проектов, использующих оба языка. Kotlin полностью совместим с Java, что позволяет использовать Kotlin в существующих Java-проектах и наоборот. Однако, для корректной работы важно учитывать несколько моментов, связанных с версиями Java и Kotlin.

### 1. **Минимальная версия Java для Kotlin**

Kotlin работает на любой версии JVM, начиная с Java 6, но рекомендуется использовать более современные версии Java для оптимальной производительности и функциональности.

- **Kotlin 1.0–1.3** поддерживает Java 6 и выше.
    
- **Kotlin 1.4 и выше** требуют как минимум **Java 8** для полноценной работы с новыми возможностями Kotlin (например, лямбда-выражениями, расширениями и функциями высшего порядка).
    
- Начиная с **Kotlin 1.5**, рекомендуется использовать **Java 11** или более позднюю версию, так как многие функции и улучшения Kotlin требуют возможностей более новых версий Java.
    

### 2. **Особенности совместимости:**

- **Явная поддержка лямбд и функциональных возможностей (Java 8 и выше):** Для работы с функциональными возможностями Kotlin, такими как лямбда-выражения и функциональные интерфейсы, требуется Java 8 и выше.
    
- **Java 9 и выше**: Если ваш проект использует такие возможности, как модули Java (Jigsaw) или специфические API, которые появились начиная с Java 9, важно использовать соответствующие версии Kotlin и JDK.
    
- **Java 15+**: Kotlin 1.4 и выше поддерживает Java 15 и более поздние версии, но важно проверять совместимость с новыми возможностями JDK, так как могут быть изменения в спецификации JVM или недокументированные изменения в байт-коде.
    

### 3. **Конфигурация Gradle для совместимости Java и Kotlin**

В `build.gradle` можно указать минимальные требования для версии Java и Kotlin:

```groovy
plugins {
    id 'org.jetbrains.kotlin.jvm' version '1.8.0'
}

java {
    toolchain {
        languageVersion = JavaVersion.VERSION_11 // Указываем Java 11
    }
}

kotlin {
    jvmToolchain(11) // Указываем, что используем Kotlin с Java 11
}
```

Здесь:

- **`languageVersion`** указывает на версию JDK, которую Gradle должен использовать.
    
- **`jvmToolchain`** указывает на версию JVM, которую использует Kotlin.
    

### 4. **Байт-код и совместимость**

При компиляции Kotlin в байт-код, он обычно компилируется в совместимый байт-код для целевой версии JVM (например, Java 8, Java 11 и так далее). Однако стоит помнить, что код, скомпилированный с использованием Kotlin, может требовать от JDK определенной версии для правильной работы.

### Резюме:

- **Kotlin поддерживает все версии Java начиная с Java 6**, но рекомендуется использовать **Java 8 или выше**.
    
- Для использования современных возможностей Kotlin и повышения совместимости с новыми функциями Java лучше использовать версии **Java 11+**.
    
- **Kotlin 1.4 и выше** требуют **Java 8+** для корректной работы, а начиная с Kotlin 1.5 желательно использовать **Java 11+**.
