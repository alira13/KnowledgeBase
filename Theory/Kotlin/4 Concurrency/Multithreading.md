# Многопоточность

Одна заметка на всю тему: от `Thread` до happens-before, замков и deadlock. Про корутины — [[Coroutines]].

---

## 1. Процесс и поток

**Процесс** — запущенная программа со своей изолированной памятью.
**Поток** — наименьшая единица выполнения, которую планирует ОС.

```text
процесс
 ├── поток 1  ─┐
 ├── поток 2  ─┼─ общий heap (объекты, поля)
 └── поток 3  ─┘   у каждого свой стек
```

Аналогия:

> Секретарь выполняет задачи по очереди — это один поток. Добавили второго секретаря — они работают параллельно и независимо.

В приложении изначально есть один поток — **main**. В Android он же рисует интерфейс, поэтому его называют UI-потоком.

---

## 2. Зачем и чем платим

**Зачем:** не блокировать интерфейс, использовать все ядра процессора, ждать сеть и не простаивать.

**Чем платим:** появляется общая изменяемая память, а значит — гонки, невидимые изменения и взаимные блокировки. Всё, что ниже, посвящено этой цене.

---

## 3. Создание потока

В Java — через `Thread` и `Runnable`:

```kotlin
val t = Thread {
    repeat(100) { println(Thread.currentThread().name) }
}
t.name = "myThread"
t.start()            // именно start(), а не run()
```

В Kotlin короче — функция `thread`:

```kotlin
thread(name = "myThread") {
    repeat(100) { println(Thread.currentThread().name) }
}
```

Под капотом то же самое, но `start = true` по умолчанию.

Частая ошибка на собеседовании:

```text
t.run()    → просто вызов метода в текущем потоке
t.start()  → создаёт новый поток ОС
```

`Thread.sleep(1000)` усыпляет **текущий** поток.

---

## 4. Демон-потоки

Потоки JVM делятся на два вида:

```text
user (non-daemon) → JVM не завершится, пока жив хотя бы один
daemon            → JVM не ждёт их и убивает при выходе
```

`main` — пользовательский. Классический демон — поток сборщика мусора, см. [[Garbage collector]].

```kotlin
thread(isDaemon = true) {
    while (true) { println("я демон"); sleep(1000) }
}
```

Что важно помнить:

- флаг ставится **до** `start()`;
- поток наследует «демонность» от родителя;
- демона могут убить в любой момент — `finally` и закрытие ресурсов могут не выполниться, поэтому важную работу с файлами и соединениями в демонах не держат.

---

## 5. Почему потоки не создают вручную

```kotlin
repeat(10_000) {
    thread { workWithImage(Image(it)) }    // так делать нельзя
}
```

Три проблемы:

```text
1. создание потока — дорого по времени
2. поток занимает память (стек ~1 МБ) → OutOfMemoryError
3. управление жизненным циклом: чтобы отменить, нужно где-то хранить все потоки
```

Решение — **пул потоков**: несколько потоков создаются один раз и переиспользуются.

Важная деталь про число потоков:

> Если ядер два, а потоков четыре, они будут постоянно переключаться на ядрах. Это **псевдопараллелизм**: переключение стоит времени. Для вычислений число потоков берут равным числу ядер.

## 6. ExecutorService

Менеджер, который владеет пулом потоков и очередью задач.

```text
задача → есть свободный поток?
             да  → выполняется
             нет → встаёт в очередь и ждёт освобождения
```

| Фабрика | Что делает | Когда |
| --- | --- | --- |
| `newFixedThreadPool(n)` | ровно `n` потоков | вычисления, `n` = число ядер |
| `newSingleThreadExecutor()` | один поток, задачи строго по очереди | фоновая работа, которая должна идти последовательно |
| `newCachedThreadPool()` | создаёт потоки по мере надобности | много ожидающих задач (сеть), но стоит ограничивать |
| `newScheduledThreadPool(n)` | с задержкой и периодически | таймеры, периодические задачи |

```kotlin
val executor = Executors.newFixedThreadPool(3)

executor.execute { println("без результата") }          // Runnable

val future: Future<String> = executor.submit(Callable {  // Callable
    Thread.sleep(1000)
    "результат"
})
println(future.get())      // get() БЛОКИРУЕТ поток, пока результат не готов

executor.shutdown()        // обязательно, иначе приложение не завершится
```

```text
execute → Runnable, результата нет
submit  → Callable, возвращает Future
```

## 7. Callback и почему появились корутины

Долгую операцию вынесли в поток — но как вернуть результат? Через колбэк:

```kotlin
private fun loadBook(callback: (Book) -> Unit) {
    thread {
        Thread.sleep(3000)
        callback(Book("1984", 1949))
    }
}
```

Пока операция одна — терпимо. Когда их несколько подряд, начинается **callback hell**:

```kotlin
loadBook { book ->
    loadAuthor { author ->
        runOnUiThread {          // ещё и вернуться в UI-поток вручную
            loadBtn.isEnabled = true
        }
    }
}
```

Три проблемы разом: растущая вложенность, ручное возвращение в главный поток и негде обрабатывать ошибки.

Именно это решают корутины — код становится последовательным. См. [[Coroutines]].

## 8. Race condition

`count++` выглядит одной операцией, но это **три**:

```text
прочитать → прибавить → записать
```

```kotlin
var count = 0
fun increment() { count++ }      // не атомарно
```

Два потока читают `5`, оба прибавляют, оба пишут `6` — один инкремент потерян. Запустите 10 потоков по 1000 инкрементов и получите не 10000, а случайное число меньше.

## 9. Проблема видимости и happens-before

Гонка — не единственная беда. Поток может **вообще не увидеть** запись другого потока:

```kotlin
var ready = false
var data = 0

// Поток A
data = 42
ready = true

// Поток B
while (!ready) { }
println(data)      // может напечатать 0 (!)
```

Причина: каждый поток кэширует переменные в регистрах и кэше ядра, а компилятор и процессор вправе **переупорядочивать** инструкции.

**JMM (Java Memory Model)** описывает, когда запись гарантированно видна. Ключевое отношение — **happens-before**:

> Если A happens-before B, то всё, что сделал A до точки синхронизации, видно B после неё.

Основные правила:

```text
программный порядок внутри одного потока
выход из synchronized  hb  вход в тот же монитор
запись volatile        hb  чтение той же переменной
Thread.start()         hb  код запущенного потока
код потока             hb  join()
транзитивность: A hb B, B hb C ⇒ A hb C
```

---

## 10. volatile

```kotlin
@Volatile var ready = false
```

Даёт **видимость** и запрет переупорядочивания. Не даёт **атомарности**:

```kotlin
@Volatile var counter = 0
counter++          // всё ещё гонка: read-modify-write из трёх шагов
```

Правило:

```text
volatile      → видимость, но не атомарность
synchronized  → видимость И атомарность
Atomic*       → видимость И атомарность, без блокировки
```

---

## 11. Атомарные типы и CAS

```kotlin
val counter = AtomicInteger(0)
counter.incrementAndGet()
```

Внутри — **CAS (compare-and-set)**: «если значение всё ещё равно ожидаемому, замени». Если не равно — повторить. Блокировки нет, поток не засыпает.

Отсюда особенность: при высокой конкуренции CAS крутится в цикле и может проиграть замку.

## 12. synchronized и монитор

У **каждого** объекта на JVM есть встроенный замок — **монитор**.

```kotlin
val lock = Any()
var count = 0

fun increment() {
    synchronized(lock) { count++ }
}
```

Две гарантии сразу:

```text
1. взаимное исключение — внутри блока только один поток
2. видимость — happens-before между выходом и входом
```

В Kotlin `synchronized` — не ключевое слово, а inline-функция; есть и аннотация `@Synchronized` (эквивалент `synchronized(this)`).

**Реентерабельность:** поток, уже владеющий монитором, может войти в него повторно.

Разные объекты — разные мониторы: потоки, синхронизированные по разным замкам, друг друга не остановят.

### Какой объект брать под замок

```text
✅ приватный val lock = Any()   — снаружи никто не захватит
⚠️ this                        — монитор публичен, чужой код может подвесить класс
❌ String-литерал, Integer      — интернируются, замок окажется общим на всё приложение
❌ var-поле                     — переприсвоят, и защита исчезнет
```

## 13. Double-checked locking

Классическая задача: потокобезопасный синглтон без блокировки на каждом вызове.

```kotlin
class Singleton private constructor() {
    companion object {
        @Volatile private var instance: Singleton? = null   // @Volatile обязателен

        fun getInstance(): Singleton =
            instance ?: synchronized(this) {
                instance ?: Singleton().also { instance = it }
            }
    }
}
```

Почему `@Volatile` критичен: без него другой поток может увидеть **не полностью сконструированный** объект — компилятор вправе переупорядочить «выделить память → записать ссылку → выполнить конструктор».

В Kotlin это обычно не нужно: `object Singleton { }` потокобезопасен по построению, а `by lazy { }` использует режим `SYNCHRONIZED`.

## 14. Замки, мьютексы, семафоры

| Примитив | Что даёт |
| --- | --- |
| `synchronized` | простая защита короткой секции |
| `ReentrantLock` | `tryLock()`, таймауты, честная очередь, `Condition` |
| `ReadWriteLock` | много читателей **или** один писатель |
| `Semaphore` | доступ ровно N потокам |
| `Mutex` (kotlinx) | для корутин: **приостанавливает**, а не блокирует поток |

```kotlin
val lock = ReentrantLock()
fun safeIncrement() = lock.withLock { count++ }   // withLock сам делает finally { unlock() }
```

Mutex — частный случай семафора с одним разрешением.

**В корутинах `synchronized` использовать нельзя**: он блокирует поток диспетчера, а если внутри окажется suspend-вызов — корутина уснёт, удерживая монитор.

## 15. Deadlock

Два потока навсегда ждут ресурсы друг друга:

```text
поток A: держит lock1, ждёт lock2
поток B: держит lock2, ждёт lock1
```

**Четыре условия Коффмана** — deadlock возможен, только если выполнены все:

```text
1. Mutual exclusion — ресурс нельзя разделить
2. Hold and wait    — держит один, ждёт другой
3. No preemption    — отобрать нельзя
4. Circular wait    — цикл ожидания
```

Как избежать: захватывать замки **всегда в одном порядке** (разрушает условие 4), использовать `tryLock()` с таймаутом, минимизировать вложенные блокировки.

Смежные проблемы:

```text
livelock   → потоки активны, но не продвигаются
starvation → поток не получает ресурс из-за нечестного планирования
```

## 16. Потокобезопасность: четыре стратегии

От лучшей к худшей.

**1. Не делить состояние.** Локальные переменные лежат в стеке потока и безопасны всегда. В Android это основной приём: UI трогаем только с main-потока.

**2. Неизменяемость.** У объекта без изменяемого состояния гонок нет:

```kotlin
data class User(val name: String, val age: Int)   // только val
```

Поэтому MVI-state делают неизменяемым и обновляют через `copy()`.

**3. Синхронизация.** Защищать доступ **и на запись, и на чтение** — синхронизация только записи не помогает, читатель увидит устаревшее значение.

**4. Готовые структуры:**

| Небезопасно | Замена |
| --- | --- |
| `HashMap` | `ConcurrentHashMap` |
| `ArrayList` | `CopyOnWriteArrayList` |
| счётчик `Int` | `AtomicInteger` |
| очередь между потоками | `LinkedBlockingQueue` |

Важно: потокобезопасность отдельных операций **не делает потокобезопасной их комбинацию**.

```kotlin
if (!map.containsKey(key)) map[key] = compute()   // гонка, оба потока пройдут проверку
map.putIfAbsent(key, compute())                   // атомарно
```

## 17. Android: специфика

```text
UI можно трогать только из main-потока
блокировка main дольше ~5 секунд → ANR
```

Обновление интерфейса из фонового потока — исключение `CalledFromWrongThreadException`. Вернуться в главный поток можно через `runOnUiThread`, `Handler` или, что правильнее, через корутину на `Dispatchers.Main`.

Устройство самого UI-потока — `Looper` и `MessageQueue`, см. [[Handler, Looper, MessageQueue]]. Про ANR — [[ANR. Application Not Responding]].

## 19. Вопросы-ловушки

- **Чем `start()` отличается от `run()`?** `run()` — обычный вызов метода в текущем потоке, новый поток создаёт только `start()`.
- **Достаточно ли `@Volatile` для `counter++`?** Нет: volatile даёт видимость, но не атомарность.
- **Почему поток B может не увидеть запись потока A?** Кэширование и переупорядочивание инструкций; нужна связь happens-before.
- **Зачем `@Volatile` в double-checked locking?** Чтобы не отдать ссылку на недостроенный объект.
- **Заблокируют ли друг друга два `@Synchronized`-метода одного объекта?** Да, монитор общий (`this`). У разных объектов — нет.
- **Что быстрее: `synchronized` или `AtomicInteger`?** Обычно атомарки, но при высокой конкуренции CAS крутится в цикле.
- **Почему нельзя брать `String`-литерал под замок?** Литералы интернируются — замок окажется общим на всё приложение.
- **Что произойдёт, если не вызвать `shutdown()` у executor?** Приложение не завершится: потоки пула остаются живыми.
- **Переживёт ли демон-поток завершение `main`?** Нет, JVM убьёт его, возможно посреди работы и без `finally`.
- **Сколько потоков брать для вычислений?** По числу ядер: лишние дают только переключения контекста.

## Коротко

```text
1. Потоки делят heap → гонки, невидимые изменения, deadlock.

2. count++ не атомарен. volatile даёт видимость, но не атомарность.

3. synchronized = взаимное исключение + happens-before.

4. Потоки дороги → пулы (ExecutorService) → корутины.

5. Лучшая синхронизация — не делить изменяемое состояние вообще.
```
