

**Запуск корутины**

Для запуска корутин используются корутин-билдеры

- **run-blocking** -  запускает новую корутину, но блокирует текущий поток на время вызова до тех пор, пока весь код внутри тела функции `runBlocking{}` полностью не завершит свое выполнение.

Корутины более эффективны, чем потоки, поскольку они приостанавливают и возобновляют выполнение вместо того, чтобы блокировать его. Однако в некоторых специфических случаях нам необходимо именно заблокировать поток. Например, в функции `main()` необходимо блокировать поток, иначе программа завершится, не дождавшись завершения работы корутины.

Корутин-билдер `runBlocking` запускает корутину, блокируя текущий выполняющийся поток, пока не будет завершен весь код в корутине.

Сигнатура функций `runBlocking` выглядит следующим образом:

```Kotlin
expectfun <T> runBlocking(context: CoroutineContext = EmptyCoroutineContext,
                           block:suspend CoroutineScope.() -> T): T
```

Функция принимает два параметра:

1. `context`: Предоставляет контекст корутины, представленный интерфейсом `CoroutineContext`, который является индексированным набором инстансов Element.
2. `block`: Вызываемый код корутины. Он принимает функцию типа `suspend CoroutineScope.() -> Unit`

Корутин-билдер `runBlocking{}` служит в качестве связующего элемента между обычным блокирующим кодом и библиотеками, написанными в suspend-стиле. Поэтому наиболее подходящие места для использования `runBlocking{}` это — функции `main` и тесты JUnit.

Функция `runBlocking{}`, вызываемая из функции `main()`, выглядит следующим образом:

```Kotlin
fun main() = runBlocking{
    ...
    ...
}
```

Мы использовали `runBlocking{}` для блокировки выполнения во всех функциях `main()` наших предыдущих примеров.

Поскольку `runBlocking{}` блокирует выполняющийся поток, он редко используется внутри кода в телах функций, так как потоки — это дорогие ресурсы, и блокировать их неэффективно и нежелательно.

- **launch** - запускает новую корутину, которая выполняется параллельно с остальным кодом, если внутри not suspend-функция, то будет выполнятся на одном потоке, если suspend, то в зависимости от dispatcher(а соответсвенно он может владеть одним или несколькими потоками) будет запускаться на нескольких или одном потоке

Функция `launch{}` запускает новую корутину, которая не возвращает вызывающей стороне никакого результата, но возвращает объект типа Job. Она не блокирует текущий поток. 

Мы также можем использовать объект Job для отмены выполнения корутины

- **async** - запускает корутину параллельно, аналогично launch. Однако перед запуском очередной корутины он дожидается завершения уже запущенной. Иногда, когда мы запускаем корутину, нам может потребоваться значение, которое должно быть возвращено из этой корутины обратно в поток, который ее запустил. Функция `async{}` принимает те же три параметра, что и функция `launch{}`, но вместо Job возвращает инстанс `Deferred<T>`. Получить из инстанса `Deferred<T>` результат вычислений, выполняемых в корутине, мы можем вызвав метод `await()`.

**Важно**!

При закрытии экрана или другого LifecycleOwner нужно останавливать все корутины, которые были запущены внутри него, так же и с ViewModel.  
Это надо делать, чтобы избежать ситуаций, например, когда экран закрылся, а корутина продолжает выполнять свою работу. Из-за такого некорректного поведения могут возникнуть ошибки или утечка памяти. Но! Переменные  
`lifecycleScope` и `viewModelScope` позволят не беспокоиться о жизненном цикле компонента приложения, и остановка корутин произойдёт самостоятельно.

Реализован этот процесс через вызов функции cancel у переменной coroutineContext.  
Корутины нужно закрывать (завершать выполнение), когда уничтожается ViewModel или при закрытии Activity, а также любого другого компонента с LifecycleOwner.

**launch**(иногда функции `async`) - функция для запуска корутины

**suspend** - модификатор, который определяет функцию, которая может приостановить свое выполнение и возобновить его через некоторый период времени.

  

Функция **runBlocking** блокирует вызывающий поток, пока все корутины внутри вызова runBlocking { ... } не завершат свое выполнение. В этом собственно основное отличие runBlocking от coroutineScope: coroutineScope не блокирует вызывающий поток, а просто приостанавливает выполнение, освобождания поток для использования другими ресурсами.

  

**Принцип работы**

**Suspend**

При компиляции кода из Kotlin в байт-код у каждой suspend-функции убирается ключевое слово suspend и добавляется дополнительный параметр в suspend-функцию - параметр типа Continuation. Этот параметр будет использоваться для координации работы между всеми `suspend`-функциями.  
Continuation в Java - Интерфейс, представляющий продолжение после точки приостановки, который возвращает значение  

При конвертировании в Java код корутины делится на части в тех местах, где происходит вызов `suspend`-функции.  
После того как код поделён на части, его вставляют по порядку  
`case` у `switch`. Перед вызовом функции `suspendPrint` меняется значение у переменной `label`, что позволяет двигаться по `switch` к следующему `case`.

Таким образом, корутины не блокируют JVM-поток, на котором они выполняются, а лишь откладывают выполнение кода на какое-то время.

Launch

```Kotlin
public fun CoroutineScope.launch(
    context: CoroutineContext = EmptyCoroutineContext,
    start: CoroutineStart = CoroutineStart.DEFAULT,
    block: suspend CoroutineScope.() -> Unit
): Job {
    val newContext = newCoroutineContext(context)// 1
    val coroutine = if (start.isLazy)// 2
        LazyStandaloneCoroutine(newContext, block) else// 3
        StandaloneCoroutine(newContext, active = true)// 4
    coroutine.start(start, coroutine, block)// 5return coroutine// 6
}
```

В коде выше видим параметры:

- `context` здесь не тот, к которому привыкли. Этот параметр необходим, например, если вы хотите определить, на каких потоках JVM будет происходить работа корутин, или хотите дать корутинам название для отладки в Debugger либо для установки обработчика ошибок.
- `start` определяет, когда будут запущены корутины. По умолчанию они запустятся незамедлительно. Также есть опции, чтобы корутины запустились по требованию в коде или незамедлительно, но без возможности их остановить.
- `block` — это `suspend`лямбда, в которую мы передаём код работы корутин.

Сама функция `launch` возвращает интерфейс `Job`, который ассоциируется с запущенными корутинами. Этот интерфейс позволяет отследить жизненный цикл корутин, всячески взаимодействовать с ними (например, запустить или отменить) и содержит список дочерних корутин.

В строчке 1 вызывается функция `newCoroutineContext(context)`, которая создаёт `CoroutineContext` для корутин. Это нужно, чтобы комбинировать `context`, который указан в параметрах, с тем, который является стандартным для `CoroutineScope`.

В строчках 2–4 происходит создание корутин в зависимости от того, какой `start` был указан в параметрах функции.

В строке 5 происходит старт корутин, а в 6 возвращается `Job` этих корутин.

**Dispatchers**

В JVM есть пул потоков, в которых выполняется любая программа. Пул потоков — это набор `Thread`-потоков, доступных для работы. Корутины используют эти потоки для своего выполнения.

Можно настраивать, с какими потоками будет работать корутина. Например, направить сложные вычисления или работу с сервером в оптимизированные для таких задач потоки. Эти тонкие настройки позволят корутинам работать максимально эффективно.

Чтобы определить, в каком `Thread`-потоке или потоках будет выполняться корутина, используется класс [CoroutineDispatcher](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines/-coroutine-dispatcher/).

Самостоятельно создавать класс для работы c JVM-потоками не нужно, для этого стоит использовать класс `Dispatchers`:

В этом `object`-классе определены несколько `CoroutineDispatcher`, которые следует использовать для выбора JVM-потока:

- `Dispatchers.Default` — это общая группа потоков JVM, количество которых ограничено ядрами CPU (минимум 2). Используется для моментальных вычислений, нагружая CPU устройства. Например, можно использовать для сортировки списка или для работы с JSON.
- `Dispatchers.Main` — это главный поток, который используется только для операций с UI.
- `Dispatchers.Unconfined` не привязывает корутину к конкретному потоку. Его стоит использовать, когда корутина не будет потреблять процессорное время (CPU) и работать с данными, которые ограничены определённым потоком (например, работа с пользовательским интерфейсом всегда выполняется в Main-потоке).
- `Dispatchers.IO` используется для работы с данными (например, с сервером), количество потоков не ограничено числом ядер CPU.

Если не указать CoroutineDispatcher (те же варианты Dispatchers) при запуске корутины, то будет использован тот, который задан в CoroutineContext у CoroutineScope.  
Например, при создании viewModelScope используется Dispatchers.Main. Это значит, что все корутины, запущенные без указания своего Dispatchers, будут выполняться в Main-потоке.  

[CoroutineName](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines/-coroutine-name/).

Чтобы не запутаться в запущенных корутинах, им можно задавать имя [CoroutineName](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines/-coroutine-name/). Также его можно получать.

  

Обработка ошибок в корутинах

С помощью передачи специального класса CoroutineExceptionHandler в launch

```Kotlin
// Обработчик ошибок у корутин
val handler = CoroutineExceptionHandler { context, throwable -> 
    println("Ошибочка вышла: $throwable")
}

viewModelScope.launch(handler) {
    // Теперь можно не бояться ошибиться
    delay(1000)
    throw NullPointerException()
    println("Корутина завершила свою работу")
} 
```
