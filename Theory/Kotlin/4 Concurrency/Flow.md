# Flow

Одна заметка на всю тему: от `flow { }` до `StateFlow`, буферов и обработки ошибок.

---

## 1. Что такое Flow

`Flow` — асинхронный поток значений, которые приходят не сразу, а по мере готовности.

```kotlin
val numbers: Flow<Int> = flow {
    repeat(3) {
        delay(100)      // можно приостанавливаться
        emit(it)        // отдаём значение
    }
}
```

Ментальная модель:

> Список отдаёт все значения сразу. Flow отдаёт их по одному, когда они появятся, и умеет ждать.

---

## 2. Flow против Sequence

`Sequence` тоже отдаёт элементы лениво. Разница в том, как она это делает:

```text
Sequence → синхронно, блокирует поток
Flow     → асинхронно, приостанавливает корутину
```

Внутри `Sequence` нельзя вызвать `delay` или сетевой запрос — там нет приостановки, только блокировка. Поэтому использовать её в корутине бессмысленно: вы заблокируете поток и потеряете весь смысл корутин.

Правило:

```text
данные уже в памяти, обработка синхронная → Sequence
данные приходят со временем (сеть, БД, UI) → Flow
```

См. [[3 Sequence]].

---

## 3. Flow холодный

Ключевое свойство: код внутри `flow { }` **не выполняется**, пока никто не подписался.

```kotlin
val f = flow {
    println("начали работу")
    emit(1)
}
// здесь ещё ничего не напечатано

f.collect { println(it) }   // только теперь "начали работу"
```

И на каждую подписку код запускается **заново**:

```kotlin
f.collect { }   // работа выполнена первый раз
f.collect { }   // выполнена второй раз, с нуля
```

> Холодный поток — это рецепт, а не готовое блюдо. Каждый подписчик готовит себе сам.

---

## 4. Операторы: промежуточные и терминальные

**Промежуточные** — возвращают новый Flow и ничего не запускают:

```kotlin
flow.map { it * 2 }
    .filter { it > 5 }
    .onEach { log(it) }
```

**Терминальные** — запускают поток:

```kotlin
flow.collect { }        // основной
flow.toList()
flow.first()
flow.count()
```

Модель:

```text
промежуточные → описывают, что делать
терминальный  → запускает
```

Поэтому цепочка без терминального оператора не делает ничего.

---

## 5. Холодные и горячие потоки

|  | Cold (`Flow`) | Hot (`SharedFlow`, `StateFlow`) |
| --- | --- | --- |
| Создание | `flow { }` | `MutableSharedFlow()`, `MutableStateFlow(x)` |
| Нужен ли подписчик | да, без него ничего не происходит | нет, значения живут независимо |
| Откуда эмитим | только внутри билдера | из любого места кода |
| При новой подписке | создаётся **новый** поток данных | подписчики делят **общий** поток |
| Завершение | завершается, когда данные кончились | **никогда** не завершается |

Отсюда следствие: у горячих потоков `collect` никогда не вернёт управление — подписка длится, пока её не отменят.

## 6. SharedFlow — общий поток событий

```kotlin
private val _events = MutableSharedFlow<Event>()
val events = _events.asSharedFlow()      // наружу отдаём неизменяемый
```

Три параметра, которые определяют его поведение:

```kotlin
MutableSharedFlow<Int>(
    replay = 1,                              // сколько отдать новому подписчику
    extraBufferCapacity = 0,                 // дополнительный буфер
    onBufferOverflow = BufferOverflow.SUSPEND
)
```

Применение: события, которые нужно доставить один раз — навигация, показ снекбара, ошибки.

---

## 7. StateFlow — состояние

`StateFlow` — это частный случай `SharedFlow`:

```kotlin
StateFlow<out T> : SharedFlow<T>
```

А именно — `SharedFlow` вот с такими параметрами:

```text
replay = 1                              → новый подписчик сразу получит текущее
extraBufferCapacity = 0                 → буфера нет
onBufferOverflow = DROP_OLDEST          → хранится только актуальное
+ distinctUntilChanged                  → два одинаковых значения подряд не придут
+ обязательное начальное значение
```

```kotlin
private val _state = MutableStateFlow(UiState())
val state = _state.asStateFlow()

_state.update { it.copy(isLoading = true) }   // атомарно
```

Важно: `_state.value = _state.value + 1` — **не** атомарно. Для изменения на основе текущего значения используйте `update { }`.

---

## 8. StateFlow против SharedFlow

| | SharedFlow | StateFlow |
| --- | --- | --- |
| Начальное значение | не обязательно | обязательно |
| Как обновляют | `emit()` | `value` / `update { }` |
| Что получит новый подписчик | по настройке `replay` | всегда текущее значение |
| Буфер | настраивается | нет, всегда актуальное |
| Повторы | приходят все | одинаковые подряд отбрасываются |
| Для чего | **события** | **состояние** |

Правило выбора:

```text
состояние экрана → StateFlow
разовое событие  → SharedFlow (или Channel)
```

Почему события не кладут в `StateFlow`: он отдаёт последнее значение каждому новому подписчику, и после поворота экрана снекбар покажется второй раз.

## 9. shareIn и stateIn

Превращают холодный поток в горячий.

```kotlin
val users: StateFlow<List<User>> = repository.observeUsers()   // холодный, из Room
    .stateIn(
        scope = viewModelScope,
        started = SharingStarted.WhileSubscribed(5000),
        initialValue = emptyList()
    )
```

Зачем: без этого каждый новый подписчик заново запускал бы запрос к базе.

Стратегии запуска:

```text
Eagerly           → стартует сразу, живёт пока жив scope
Lazily            → стартует с первым подписчиком, дальше живёт
WhileSubscribed   → живёт, пока есть подписчики
```

`WhileSubscribed(5000)` — стандарт для Android: пять секунд после ухода последнего подписчика поток ещё жив, поэтому поворот экрана не приводит к перезапуску запроса.

## 10. Буфер и backpressure

**Backpressure** — ситуация, когда потребитель обрабатывает данные медленнее, чем производитель их создаёт.

По умолчанию Flow работает так:

```text
emit → ждём, пока collect обработает → следующий emit
```

То есть производитель приостанавливается. Оператор `buffer` разрывает эту связь:

```kotlin
flow {
    repeat(10) { emit(it); delay(100) }       // производитель быстрый
}
.buffer(capacity = 2, onBufferOverflow = BufferOverflow.DROP_LATEST)
.collect {
    delay(1000)                                // потребитель медленный
}
```

Стратегии переполнения:

```text
SUSPEND      → производитель ждёт (по умолчанию)
DROP_LATEST  → выбрасываем новые значения
DROP_OLDEST  → выбрасываем старые, оставляем свежие
```

Родственные операторы:

```text
conflate()          → оставлять только последнее значение
collectLatest { }   → отменять обработку, если пришло новое
```

Для UI обычно нужен именно `DROP_OLDEST` или `conflate`: актуальное состояние важнее промежуточных.

## 11. flowOn — переключение контекста

По умолчанию весь поток выполняется в контексте того, кто подписался.

```kotlin
flow
    .map { heavyWork(it) }     // ①
    .flowOn(Dispatchers.IO)    // действует на ①  и на сам flow { }
    .collect { render(it) }    // здесь контекст подписчика — Main
```

Главное правило:

> `flowOn` влияет только на то, что **выше** него по цепочке. Вниз контекст не протекает.

```text
оператор 1
оператор 2
flowOn(IO)     → действует на 1 и 2
оператор 3     → выполняется в контексте подписчика
```

Если поставить два `flowOn` подряд, побеждает ближний к операторам — верхний.

Именно поэтому менять контекст внутри `flow { }` через `withContext` **нельзя** — будет ошибка о нарушении контекста. Для этого и существует `flowOn`.

## 12. Обработка исключений

Исключение возникает при обработке `emit`, то есть фактически в `collect`. Сам `collect` — обычная suspend-функция, поэтому `try/catch` вокруг него работает.

Но есть правило, которое нарушать нельзя:

> **Exception transparency.** Оборачивать `emit` в `try/catch` внутри `flow { }` запрещено: исключение будет проглочено, и подписчик о нём не узнает.

Правильный инструмент — оператор `catch`:

```kotlin
flow
    .retry(3) { e -> e is IOException }     // ① сначала повторы
    .catch { e -> emit(fallbackValue) }     // ② потом обработка
    .collect { render(it) }
```

① `retry` перезапускает цепочку — полезно, когда пропала сеть.
② `catch` ловит исключения, возникшие **выше** по цепочке, и может отдать запасное значение.

Порядок важен: сначала `retry`, потом `catch`.

Сравнение способов:

| Способ | Годится? |
| --- | --- |
| `try/catch` вокруг `collect` | работает, но нельзя сделать retry и цепочку приходится оборачивать целиком |
| `try/catch` вокруг `emit` внутри flow | **нельзя** — нарушает exception transparency |
| `CoroutineExceptionHandler` в scope | ловит, но без retry и без контекста |
| оператор `catch` + `retry` | **предпочтительный** |

## 13. Flow как состояние экрана

Схема, по которой работает почти любой экран:

```text
ViewModel хранит StateFlow<UiState>
      ↓
UI подписывается и перерисовывается
      ↓
действие пользователя → update { } → новое состояние
```

```kotlin
class UsersViewModel(repo: UserRepository) : ViewModel() {
    private val _state = MutableStateFlow(UsersState())
    val state = _state.asStateFlow()

    fun load() = viewModelScope.launch {
        _state.update { it.copy(isLoading = true) }
        val users = repo.getUsers()
        _state.update { it.copy(users = users, isLoading = false) }
    }
}
```

Почему именно `StateFlow`: состояние всегда есть, новый подписчик сразу получает актуальное, одинаковые значения подряд не вызывают лишней перерисовки.

---

## 14. Как собирать в UI

Во фрагменте — с учётом жизненного цикла:

```kotlin
viewLifecycleOwner.lifecycleScope.launch {
    repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.state.collect { render(it) }
    }
}
```

Без `repeatOnLifecycle` сбор продолжится, когда экран не виден — лишняя работа и потенциальный краш.

В Compose:

```kotlin
val state by viewModel.state.collectAsStateWithLifecycle()
```

## 15. Частые грабли

- **Цепочка без терминального оператора** ничего не делает.
- **`withContext` внутри `flow { }`** → ошибка нарушения контекста, нужен `flowOn`.
- **`try/catch` вокруг `emit`** → проглоченное исключение, используйте `catch`.
- **События в `StateFlow`** → повторный показ после поворота экрана.
- **`value = value + 1`** у `StateFlow` не атомарно, нужен `update { }`.
- **Сбор без `repeatOnLifecycle`** → работа на невидимом экране.
- **Холодный поток без `stateIn`** → запрос к базе повторяется на каждую подписку.
- **`StateFlow` конфлейтит**: два быстрых изменения подряд подписчик может увидеть как одно. Для тестов и для событий это важно.

## 16. Что знать на каком уровне

**Middle**

```text

map / filter / onEach
холодный поток
StateFlow, SharedFlow и разница между ними
```

**Middle+**

```text
flowOn и правило «действует вверх»
catch / retry, exception transparency
buffer, conflate, collectLatest
stateIn / shareIn, SharingStarted
```

**Senior**

```text
backpressure и стратегии переполнения
конфлейт StateFlow и его последствия
Flow vs Channel для событий

```

## 17. Вопросы-ловушки

- **Что произойдёт, если не вызвать терминальный оператор?** Ничего: промежуточные операторы только описывают цепочку.
- **Сколько раз выполнится код внутри `flow { }` при двух подписках?** Два раза — поток холодный.
- **Чем `StateFlow` отличается от `SharedFlow`?** Это `SharedFlow` с `replay = 1`, обязательным начальным значением и `distinctUntilChanged`.
- **Почему события нельзя хранить в `StateFlow`?** Новый подписчик получит последнее значение, и событие повторится после поворота экрана.
- **На какие операторы действует `flowOn`?** Только на те, что выше него по цепочке.
- **Почему нельзя `withContext` внутри `flow { }`?** Нарушение контекста эмиссии — Flow это проверяет и бросает исключение.
- **Что такое exception transparency?** Запрет ловить исключения вокруг `emit` внутри потока: подписчик должен узнать об ошибке.
- **Зачем `WhileSubscribed(5000)`?** Пережить поворот экрана, не перезапуская запрос.
- **Почему тест не видит промежуточное значение `StateFlow`?** Конфлейт: быстрые последовательные значения схлопываются.
- **Чем `collectLatest` отличается от `collect`?** Отменяет обработку предыдущего значения, если пришло новое.

```text
   SharedFlow = события (значения не хранятся).

3. flowOn действует вверх по цепочке.

```
