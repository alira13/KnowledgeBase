# Потокобезопасность (Thread safety)

**Потокобезопасный** код — тот, который остаётся корректным, когда его одновременно выполняют несколько потоков, без дополнительной синхронизации со стороны вызывающего. Проверка простая: если результат зависит от того, кто из потоков успел первым, — код не потокобезопасен.

## Откуда берутся проблемы
Потоки одного процесса делят **heap** (объекты, поля), но у каждого свой стек. Опасно ровно то, что разделяется и **изменяется**.

Три разных беды, которые часто путают:
1. **Race condition (гонка)** — результат зависит от порядка выполнения. Классика — `count++`: read-modify-write из трёх шагов.
2. **Проблема видимости** — поток B вообще не видит запись потока A, потому что она осела в кэше ядра или инструкции переупорядочены. См. [[Java Memory Model (happens-before)]].
3. **Нарушение инварианта** — каждая операция атомарна по отдельности, но объект успевают увидеть в промежуточном состоянии (перевели деньги со счёта, но ещё не зачислили).

```kotlin
// небезопасно: составная операция «проверил → положил»
if (!map.containsKey(key)) map[key] = compute()   // оба потока могут пройти проверку
```

## Четыре способа сделать код потокобезопасным
От лучшего к худшему — предпочитай первые, они не требуют дисциплины при каждом обращении.

### 1. Не делить состояние (confinement)
Самое надёжное — данные принадлежат одному потоку. Локальные переменные потокобезопасны всегда: они лежат в стеке потока.

В Android это основной приём: **UI трогаем только с main-потока**, работу — на фоновых, результат возвращаем обратно. Тот же принцип у корутин — «изменяем state только в одном месте» (см. [[Coroutines]]).

### 2. Неизменяемость (immutability)
У объекта без изменяемого состояния гонок нет по определению — читать можно из любого числа потоков.
```kotlin
data class User(val name: String, val age: Int)     // val, никаких var
val users: List<User> = listOf(...)                  // read-only интерфейс
```
Это причина, почему MVI-state делают `data class` с `val` и обновляют через `copy()`: вместо изменения объекта создаётся новый.

### 3. Синхронизация
Если делимое изменяемое состояние неизбежно — защищай доступ **и на запись, и на чтение**:
- `synchronized` / `ReentrantLock` — взаимное исключение, см. [[0 Threads 3 Synchronized]].
- `@Volatile` — только видимость флага, без атомарности.
- `Atomic*` — атомарные операции через CAS без блокировок.
- `Mutex` / `Semaphore` из kotlinx — для корутин, приостанавливают вместо блокировки потока.

### 4. Готовые потокобезопасные структуры
| Небезопасно | Потокобезопасная замена |
| --- | --- |
| `HashMap`, `mutableMapOf` | `ConcurrentHashMap` |
| `ArrayList`, `mutableListOf` | `CopyOnWriteArrayList` (много чтений, редкие записи) |
| `Int`-счётчик | `AtomicInteger` |
| очередь между потоками | `LinkedBlockingQueue`, `ConcurrentLinkedQueue` |

Важно: **потокобезопасность отдельных операций не делает потокобезопасной их комбинацию**. Для `ConcurrentHashMap` вместо «проверил и положил» есть атомарные `putIfAbsent`, `computeIfAbsent`, `merge`.

## Что уже потокобезопасно в Kotlin/Android
- `object` (singleton) и `by lazy { }` (режим `SYNCHRONIZED` по умолчанию) — инициализация защищена.
- `StateFlow`/`MutableStateFlow` — потокобезопасны, но `value = value + 1` — **не** атомарно; используй `update { }`.
- `String`, `Int` и другие immutable-типы.
- **`ViewModel` сам по себе не потокобезопасен**: если несколько корутин на разных диспетчерах правят одно поле — это обычная гонка.

## Цена
Синхронизация не бесплатна: блокировки дают контенцию (потоки стоят в очереди), переключения контекста и риск deadlock. Поэтому порядок предпочтений именно такой: сначала убрать разделяемое состояние, потом сделать его неизменяемым, и только затем защищать замками.

## Как проверять
- Гонки почти не воспроизводятся в отладке — нужны стресс-тесты (много потоков × много итераций) и повторные запуски.
- Android Studio ругается на обращение к UI не из main-потока; включи StrictMode для IO на main.
- Симптом гонки: «иногда падает», «раз в сто запусков неверное число», `ConcurrentModificationException`.

## Вопросы-ловушки
- Потокобезопасен ли `HashMap`, если только читать? → да, при условии, что запись полностью завершилась **до** старта читающих потоков и между ними есть happens-before; параллельная запись при чтении — уже нет.
- `val` делает объект потокобезопасным? → нет: неизменяема **ссылка**, а не содержимое. `val list = mutableListOf<Int>()` спокойно портится из двух потоков.
- Чем immutable отличается от read-only? → `List` — read-only интерфейс поверх, возможно, изменяемого списка; настоящая неизменяемость — когда изменить нельзя вообще ни через какую ссылку.
- Достаточно ли синхронизировать только запись? → нет, читатель без синхронизации может видеть устаревшее значение.
