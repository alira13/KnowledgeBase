В многопоточной обработке в Java и Kotlin можно использовать либо **`ExecutorService` (Java Concurrency API)**, либо **Kotlin Coroutines**. Давайте разберём их различия.

| **Функция**                     | **`ExecutorService` (Java)**               | **Kotlin Coroutines**               |
| ------------------------------- | ------------------------------------------ | ----------------------------------- |
| **Подход**                      | Поток-ориентированный                      | Задача-ориентированный              |
| **Создание потоков**            | Явное создание потоков                     | Управляется автоматически           |
| **Управление жизненным циклом** | Нужно вручную `shutdown()`                 | Автоматическое управление           |
| **Контроль задач**              | `Future`                                   | `Job` и `Deferred`                  |
| **Обработка исключений**        | `try-catch` в `Future.get()`               | `CoroutineExceptionHandler`         |
| **Контексты выполнения**        | `ExecutorService` определяет пул потоков   | `Dispatchers` управляют контекстами |
| **Отмена задач**                | `future.cancel(true)` (может не сработать) | `job.cancel()` (немедленная отмена) |
| **Блокировка потока**           | `Future.get()` блокирует поток             | `suspend` функции **не блокируют**  |

### Coroutines
[https://habr.com/ru/companies/otus/articles/766774/](https://habr.com/ru/companies/otus/articles/766774/)

**Корутины** (от англ. **coroutine** — «сопрограмма») — это инструмент для решения задач многопоточности, 
 - позволяют выполнять долгие задачи асинхронно не блокируя JVM-поток. Эти задачи создаются в suspend-функциях, которые могут приостановить свое выполнение и возобновить в точке остановки. 
 - корутины= “легковесные потоки” (lightweight threads), что по сути означает, что мы можем выполнять код с корутинами аналогично тому, как мы выполняем код с потоками, но легковесные они, потому что требуют меньше ресурсов для своего запуска по сравнению с потоками.


### Создание корутин
1. `CoroutineScope` Выбрать или создать scope
2. `CoroutineContext` Передать  CoroutineContext в scope: 
	1. `CoroutineName` Имя корутины, Удобное имя для отладки корутин
	2. `Dispatcher` Диспатчер определяет, в каком потоке выполняется корутина
	3. `Job` Управляет жизненным циклом корутины (можно отменить корутину)          
	4. `ExceptionHandler` Обрабатывает исключения внутри корутины   
3. `Suspend` Описать код, который должен выполнятся в корутине
4. `CoroutineBuilder` Передать этот код в корутин-билдер, который его автоматом запустит

Отследить жизненный цикл корутины самостоятельно можно при помощи переменных:

- `isActive` — корутина активна;
- `isCancelled` — отменена;
- `isCompleted` — завершилась.

Промежуточные состояния в виде `Completing` (завершается) и `Cancelling` (отменяется) имеют пометку `await children` (англ. «ожидаем детей»).

Родство здесь ожидаемо — у корутин могут быть дочерние корутины, которые как раз называют детьми или потомками.

### Правила StructuredConcurrency
Структурированный параллелизм -принципы работы с корутинами

**Structured concurrency в Kotlin** — это подход, используемый в **Kotlin Coroutines**, который помогает управлять асинхронными задачами безопасно и предсказуемо. Он гарантирует, что все запущенные корутины имеют жизненный цикл, привязанный к их родительскому `CoroutineScope`, что предотвращает утечки и ошибки при работе с многопоточностью.

## 🔹 **Основные принципы structured concurrency в Kotlin**

### ✅ **1. Все корутины должны создаваться внутри определенного Scope

Корутинный scope управляет жизненным циклом корутин.
Все корутины создаются внутри `CoroutineScope`, который имеет свой жизненный цикл. 
Scope отвечает за ЖЦ корутин, например отмену. Это предотвращает утечки и зависшие задачи. То есть на практике у нас должна быть возможность отменить scope и корутины все внутри него отменяются. Когда например пользователь уходит с экрана
 
 Отмена scope 
 `scope.cancel
Если используете **свой** `CoroutineScope`, то **его нужно отменять в `onDestroy()`**.
GlobalScope нарушает принципы. Его никогда не надо использовать. Надо создавать свои scope
```kotlin
suspend fun fetchData() {
    coroutineScope { // Этот scope завершится только когда все вложенные корутины завершатся
        launch { loadUser() }
        launch { loadPosts() }
    }
    println("Все данные загружены") // Выполнится только после завершения всех вложенных задач
}
```

### ✅ **2. В корутинах все объекты job имеют иерархию. То есть есть родительский job и его дочерние. 

При этом при создании scope и передачи context у нас автоматом создается родительская job.

### ✅ **3 Если родительская корутина завершится или выбросит исключение, все дочерние корутины автоматически отменяются.Но отмена дочерней корутины не отменяет родительскую.

```kotlin
suspend fun fetchData() {
    coroutineScope {
        val job = launch {
            repeat(100) {
                delay(100)
                println("Работаем: $it")
            }
        }

        delay(300) // Через 300 мс scope завершится
        println("Отмена работы")
    } // job автоматически отменится здесь
}
```

✅ Без structured concurrency нам пришлось бы вручную отменять `job`.

---
### ✅ 4 **Родительская корутина не завершается до тех пор, пока живет дочерняя**

✅ 5 Если в дочерней корутине произошло исключение, оно передается наверх родительским

### ✅ **3. `SupervisorScope` позволяет дочерним задачам работать независимо**

По умолчанию, если одна корутина выбрасывает исключение, все остальные тоже отменяются.  
Но если используется `supervisorScope`, то сбой одной корутины **не влияет** на другие.

```kotlin
suspend fun fetchData() {
    supervisorScope { // Не отменяет другие корутины при ошибке одной из них
        launch {
            throw RuntimeException("Ошибка в корутине!")
        }
        launch {
            delay(1000)
            println("Вторая корутина продолжает работать!")
        }
    }
}
```

---

### ✅ **4. `withContext` для безопасного переключения контекста**

`withContext` **не создаёт новую корутину**, а просто переключает контекст выполнения. В отличие от `launch`, он дожидается выполнения блока.

```kotlin
suspend fun loadData(): String = withContext(Dispatchers.IO) {
    // Код внутри выполняется в IO-потоке, но `withContext` завершится перед выходом из функции
    delay(1000)
    "Данные загружены"
}
```
