# Thread, Lock, Mutex, Deadlock

## Thread (поток)
Наименьшая единица выполнения, которую планирует ОС. Внутри процесса потоки делят общую память (heap), но имеют свой стек. Проблема общей памяти — **гонки данных** (race condition), когда результат зависит от порядка выполнения. См. [[0 Threads 3 Synchronized]], [[Thread safety]].

## Lock (блокировка)
Примитив синхронизации: поток захватывает lock перед доступом к разделяемому ресурсу и освобождает после. Пока lock занят, другие потоки ждут.
- `synchronized` — встроенный монитор объекта (неявный lock).
- `ReentrantLock` — явный lock, поддерживает `tryLock()`, таймауты, **fairness** (честная очередь), несколько `Condition`.
- `ReadWriteLock` — раздельные блокировки на чтение (много читателей) и запись (один писатель).

```kotlin
val lock = ReentrantLock()
lock.withLock { /* критическая секция */ }
```

## Mutex (mutual exclusion)
Взаимное исключение — гарантия, что в критической секции одновременно только один поток/корутина.
- В корутинах используют `kotlinx.coroutines.sync.Mutex` — **suspending**, не блокирует поток:

```kotlin
val mutex = Mutex()
mutex.withLock { counter++ }   // корутина приостанавливается, поток свободен
```

Отличие от блокирующего `synchronized`: `Mutex.lock()` приостанавливает корутину, а не занимает поток ожиданием. См. [[2 Coroutines. Synchronization]].

## Semaphore
Разрешает доступ N потокам одновременно (пул разрешений). Mutex — частный случай семафора с 1 разрешением.

## Deadlock (взаимоблокировка)
Два+ потока навсегда ждут ресурсы друг друга. Классика: поток A держит lock1 и ждёт lock2, поток B держит lock2 и ждёт lock1.

**4 условия Коффмана** (все должны выполниться):
1. Mutual exclusion — ресурс нельзя разделить.
2. Hold and wait — держит один ресурс, ждёт другой.
3. No preemption — ресурс нельзя отобрать принудительно.
4. Circular wait — циклическая цепочка ожидания.

**Как избежать:**
- Всегда захватывать блокировки в **одном порядке** (разрушает circular wait).
- `tryLock()` с таймаутом вместо бесконечного ожидания.
- Минимизировать вложенные блокировки; уменьшать размер критических секций.

**Смежные проблемы:** livelock (потоки активны, но не прогрессируют), starvation (поток не получает ресурс из-за нечестного планирования).
