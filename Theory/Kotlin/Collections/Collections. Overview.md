# Коллекции — обзор

**Коллекция** — группа элементов переменного размера, которой удобно оперировать как одним объектом. В Kotlin три базовых вида:

- **List** — упорядоченная последовательность, доступ по индексу, дубликаты разрешены. Пример — предложение: порядок важен, слова могут повторяться.
- **Set** — множество уникальных элементов, порядок обычно не важен. Пример — алфавит.
- **Map** — пары «ключ → значение», ключи уникальны, значения могут дублироваться. Пример — ID сотрудника → должность.

## Read-only и mutable
У каждого вида два интерфейса: **read-only** (`List`, `Set`, `Map`) и **mutable** (`MutableList`, ...), который добавляет операции изменения. В Java такого разделения нет — там `List` изменяемый всегда; Kotlin надстроил его над теми же реализациями.

```kotlin
val list = listOf(1, 2, 3)              // List — нет add/remove
val mutable = mutableListOf(1, 2, 3)    // MutableList — есть
```

### val/var и mutable — про разное
Это самая частая путаница:
- **`val`/`var`** — про **ссылку**: можно ли присвоить переменной другую коллекцию.
- **read-only/mutable** — про **содержимое**: можно ли добавлять и удалять элементы.

```kotlin
val list = mutableListOf(1)
list.add(2)        // ✅ содержимое меняется
// list = mutableListOf()  ❌ ссылку переприсвоить нельзя
```
Поэтому изменяемую коллекцию не нужно объявлять через `var`.

### Read-only ≠ immutable
`listOf()` возвращает **интерфейс без методов изменения**, но под ним лежит обычный изменяемый `ArrayList`. Приведение типа вскрывает его:
```kotlin
val readOnly: List<Int> = mutableListOf(1, 2)
(readOnly as MutableList).add(3)      // сработает!
```
А ещё read-only-ссылка может «меняться сама», если кто-то держит mutable-ссылку на ту же коллекцию. Настоящая неизменяемость — `kotlinx.collections.immutable` или защитная копия (`toList()`).

## Иерархия и реализации
Интерфейсы Kotlin — свои, а реализации взяты из Java: `ArrayList`, `LinkedList`, `HashMap`, `HashSet`, `TreeMap`.

| Что вызываем | Что получаем на самом деле | Особенность |
| --- | --- | --- |
| `listOf`, `mutableListOf` | `ArrayList` | динамический массив |
| `setOf`, `mutableSetOf` | `LinkedHashSet` | **сохраняет порядок вставки** |
| `mapOf`, `mutableMapOf` | `LinkedHashMap` | **сохраняет порядок вставки** |
| `hashSetOf`, `hashMapOf` | `HashSet`, `HashMap` | порядок не гарантирован, чуть быстрее |
| `sortedSetOf`, `sortedMapOf` | `TreeSet`, `TreeMap` | отсортированы, O(log n) |

Полезная деталь для собеседования: `mapOf` в Kotlin — именно `LinkedHashMap`, поэтому итерация идёт в порядке добавления, в отличие от голого `HashMap` в Java.

## ArrayList vs LinkedList
- **ArrayList** — динамический массив: элементы лежат подряд, доступ по индексу O(1). При переполнении создаётся новый массив в **1,5 раза** больше (`oldCapacity + (oldCapacity shr 1)`) и данные копируются — поэтому добавление в конец амортизированно O(1), а вставка в начало O(n) (сдвиг всех элементов).
- **LinkedList** — двусвязный список: вставка/удаление по краям O(1), но доступ по индексу O(n) (обход по ссылкам) и заметный расход памяти на узлы.

На практике в Android почти всегда `ArrayList`: непрерывная память дружелюбна к кэшу процессора, а вставки в середину редки. См. [[ArrayList]], [[LinkedList]], [[Complexity table]].

## HashMap изнутри
Самый частый вопрос про коллекции. HashMap — **массив бакетов**, каждый бакет — связный список (или дерево).

**Как кладётся элемент:**
1. Считается `key.hashCode()` (Int) и дополнительно перемешивается: `h xor (h ushr 16)` — чтобы старшие биты влияли на результат.
2. Индекс бакета вычисляется как `(n - 1) and hash`, где `n` — размер массива. Именно поэтому размер всегда **степень двойки**: побитовое `and` заменяет дорогое взятие остатка.
3. Бакет пуст → кладём.
4. Бакет занят (**коллизия**) → сравниваем ключи: сначала `hashCode`, потом `equals`. Совпало — значение перезаписывается, нет — элемент добавляется в конец списка.

**Поиск** — тот же путь: хеш → бакет → перебор внутри бакета через `equals`. Отсюда сложность: O(1) в среднем, O(n) в вырожденном случае, когда все ключи попали в один бакет.

**Load factor и resize.** При заполнении на **0,75** массив увеличивается **вдвое**, и все элементы перераспределяются (rehash) — операция дорогая. Если знаешь размер заранее, задай ёмкость в конструкторе.

**Treeification.** Если в одном бакете накопилось **8** элементов (и массив не меньше 64), список превращается в **красно-чёрное дерево** — поиск внутри бакета становится O(log n) вместо O(n). Это защита от атак на коллизии. При уменьшении до 6 дерево сворачивается обратно.

Из этого следует главное практическое правило: **ключ HashMap должен корректно реализовывать `equals`/`hashCode` и быть неизменяемым**. Изменил поле, участвующее в хеше, — элемент остался в старом бакете и «потерялся». См. [[Classes. toString, equals, hashCode, copy]].

`HashSet` — это `HashMap`, где значения-заглушки, поэтому механика та же. См. [[Set]].

## Что выбрать
| Задача | Структура |
| --- | --- |
| Хранить по порядку, читать по индексу | `ArrayList` |
| Проверять «есть ли элемент» | `HashSet` — O(1) вместо O(n) у списка |
| Поиск по ключу | `HashMap` |
| Нужен отсортированный обход | `TreeMap` / `TreeSet` |
| Много потоков | `ConcurrentHashMap` — см. [[Multithreading]] |

## Грабли
- `ConcurrentModificationException` — изменение коллекции во время итерации. Решения: `iterator.remove()`, `removeAll { }`, обход копии.
- `map[key]` возвращает `V?`, а не `V` — отсутствующий ключ и хранимый `null` неразличимы без `containsKey`.
- Kotlin-функции `filter`, `map` создают **новые** коллекции на каждом шаге. Для длинных цепочек на больших данных — `asSequence()`, см. [[3 Sequence]].
- `List.contains` — O(n). В цикле по другому списку это незаметно превращается в O(n²); замена на `Set` решает.
- `arrayOf` и `listOf` — разное: массив имеет фиксированный размер и инвариантен по типу.

## Вопросы-ловушки
- Чем `val` отличается от immutable-коллекции? → `val` фиксирует ссылку, содержимое `mutableListOf` при этом свободно меняется.
- Почему размер таблицы HashMap — степень двойки? → чтобы индекс считался быстрым `(n-1) and hash` вместо `%`.
- Что будет, если `hashCode` всегда возвращает 1? → всё попадёт в один бакет, HashMap выродится в список: O(n) вместо O(1) (после 8 элементов — в дерево, O(log n)).
- Гарантирует ли `mapOf` порядок? → в Kotlin да, это `LinkedHashMap`; у чистого `HashMap` — нет.
- Сколько занимает добавление в конец `ArrayList`? → амортизированно O(1), но в момент расширения O(n) с копированием.
