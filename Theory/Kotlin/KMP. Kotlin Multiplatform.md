# KMP. Kotlin Multiplatform

Технология Kotlin для **шеринга кода между платформами** (Android, iOS, desktop, web, backend). Идея: общая **бизнес-логика** (domain, data, сеть, БД, валидация) на Kotlin, а **UI нативный** на каждой платформе — либо общий через Compose Multiplatform.

Главное отличие от кроссплатформенных фреймворков: KMP не приносит свой рантайм и свой рендер. Общий код **компилируется в нативный формат каждой платформы** — в JVM-байткод для Android и в нативный бинарник для iOS. Приложение остаётся нативным, общей становится только логика.

## Что шарят и что нет
- **Шарят**: доменные модели, use cases, репозитории, сетевой слой (Ktor), БД (SQLDelight/Room KMP), валидацию, DI, часто и ViewModel-логику.
- **Нативно (обычно)**: UI (Jetpack Compose на Android, SwiftUI на iOS), платформенные API — камера, биометрия, уведомления, разрешения.

Практическое правило: чем ближе к данным, тем выгоднее шарить; чем ближе к пользователю, тем дороже.

## Source sets и иерархия
- **commonMain** — общий код, доступны только мультиплатформенные API (никакого `java.*`).
- **androidMain**, **iosMain**, **desktopMain** — платформенные реализации.
- **commonTest**, **androidUnitTest** и т.д. — то же для тестов.

Между общим и платформенным есть **промежуточные** наборы. `iosMain` — как раз такой: под ним живут три реальных таргета (`iosX64`, `iosArm64`, `iosSimulatorArm64`), и код пишется один раз для всех трёх. Современный Gradle-плагин расставляет эту иерархию автоматически (default hierarchy template) — вручную объявлять `dependsOn` больше не нужно.

## expect / actual
Механизм платформенных реализаций: в `commonMain` объявляется контракт, в каждом таргете — реализация.
```kotlin
// commonMain
expect fun platformName(): String

// androidMain
actual fun platformName() = "Android ${Build.VERSION.SDK_INT}"

// iosMain
actual fun platformName() = UIDevice.currentDevice.systemName()
```
Работает для функций, свойств и классов. Для классов удобен `actual typealias` — когда на платформе уже есть подходящий тип:
```kotlin
// commonMain
expect class DateFormatter { fun format(millis: Long): String }

// androidMain — просто указываем существующий класс
actual typealias DateFormatter = AndroidDateFormatter
```

### Альтернатива: интерфейс + DI (чаще лучше)
`expect/actual` жёстко связывает общий код с платформенным на уровне компиляции: реализация обязана существовать для **каждого** таргета, и подменить её в тестах нельзя. Поэтому в продакшене чаще используют обычный интерфейс, а реализацию отдают через DI:
```kotlin
// commonMain
interface PlatformInfo { val name: String }

// androidMain
class AndroidPlatformInfo : PlatformInfo { override val name = "Android" }

// в тестах — FakePlatformInfo, никакого expect/actual
```
Плюсы: тестируемость, возможность иметь несколько реализаций, отсутствие обязательства покрыть все таргеты. `expect/actual` остаётся для случаев, где интерфейс избыточен: константы, тонкие обёртки над платформенным API.

## Ключевые библиотеки
| Задача | Библиотека |
| --- | --- |
| Сеть | **Ktor Client** |
| JSON | **kotlinx.serialization** |
| БД | **SQLDelight**, Room KMP |
| Асинхронность | **kotlinx.coroutines** |
| Дата и время | **kotlinx.datetime** |
| DI | **Koin** (мультиплатформенный; Hilt — только Android). См. [[Koin]] |
| Настройки | multiplatform-settings |
| UI (опционально) | **Compose Multiplatform** |
| Тесты | `kotlin.test` в `commonTest` |

## Compose Multiplatform
Общий UI на Compose поверх KMP: Android, iOS, desktop и web. iOS-таргет доведён до стабильного состояния и используется в проде, но есть нюансы — интеграция с нативной навигацией, отличия в жестах и скролле, размер бинарника.

Выбор — компромисс: общий UI экономит много кода, нативный даёт привычный пользователю UX и полный доступ к платформенным контролам. Промежуточный вариант, который часто и выбирают: общая логика + нативный UI, а Compose Multiplatform точечно для отдельных экранов.

## Тестирование
Тесты общего кода живут в `commonTest` и выполняются на **всех** таргетах — это ценно: одна и та же логика проверяется и на JVM, и на Native.
```kotlin
// commonTest
class ValidatorTest {
    @Test fun `rejects empty email`() { assertFalse(EmailValidator.isValid("")) }
}
```
Для корутин в общем коде — `runTest` из `kotlinx-coroutines-test`. См. [[Test. Coroutines and Flow]].

## Плюсы и минусы
**За:** меньше дублирования логики, единый источник правды бизнес-правил, нативные UX и производительность, **постепенное внедрение** — можно вынести в общий модуль один слой и не переписывать приложение.

**Против:** порог входа и настройка тулчейна; интероп с iOS (см. [[KMP. iOS integration]]); библиотек меньше, чем в нативной экосистеме; для сборки iOS нужен Mac; отладка общего кода из Xcode менее удобна; команде нужны люди, готовые читать Kotlin на iOS-стороне — это чаще организационная проблема, чем техническая.

## KMP vs Flutter / React Native
| | KMP | Flutter / RN |
| --- | --- | --- |
| Что шарится | логика (UI опционально) | логика **и** UI |
| UI | нативный | свой рендер (Flutter) или мост к нативному (RN) |
| Производительность | нативная | близкая, но с прослойкой |
| Внедрение в существующее приложение | по одному модулю | обычно отдельный экран/контейнер |
| Доступ к платформенным API | напрямую | через плагины/мосты |

KMP — это «натив с общей логикой», а не замена нативной разработки.

## Вопросы-ловушки
- Что нельзя использовать в `commonMain`? → платформенные API, в том числе `java.*`: общий код компилируется и в нативный бинарник.
- Когда `expect/actual`, а когда интерфейс? → интерфейс + DI по умолчанию (тестируемость, гибкость); `expect/actual` для тонких обёрток и констант.
- Зачем `iosMain`, если таргетов три? → промежуточный source set: код пишется один раз для arm64, x64 и симулятора.
- Шарится ли UI в KMP? → по умолчанию нет; опционально — через Compose Multiplatform.
- Чем KMP отличается от Flutter? → KMP не приносит свой рендер: UI остаётся нативным, общей становится логика.
