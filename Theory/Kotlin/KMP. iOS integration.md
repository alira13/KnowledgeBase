# KMP: интеграция с iOS

Самая непростая часть KMP — стык общего Kotlin-кода с iOS-приложением. Общий контекст — [[KMP. Kotlin Multiplatform]].

## Как Kotlin попадает в Xcode
**Kotlin/Native** компилирует общий код в нативный бинарник и оборачивает его во **framework** с Objective-C-совместимым заголовком. Swift видит его как обычную библиотеку.

```kotlin
kotlin {
    listOf(iosX64(), iosArm64(), iosSimulatorArm64()).forEach { target ->
        target.binaries.framework {
            baseName = "Shared"
            isStatic = true
        }
    }
}
```
Три таргета — это устройство (arm64), симулятор на Apple Silicon и симулятор на Intel. Чтобы отдать все сразу одним артефактом, собирают **XCFramework**.

Способы подключения к Xcode-проекту:
| Способ | Когда |
| --- | --- |
| Прямая зависимость на framework + Gradle-таск в Build Phases | монорепозиторий, Kotlin и iOS рядом |
| **CocoaPods** (плагин `cocoapods`) | в проекте уже CocoaPods |
| **Swift Package Manager** — публикация XCFramework | современный вариант, iOS-разработчики предпочитают его |

Ключевое организационное решение: собирают ли iOS-разработчики Kotlin-код сами (нужен настроенный тулчейн, Gradle, JDK) или получают готовый бинарник из CI. Второй путь заметно снижает трение в команде.

## Как Kotlin выглядит из Swift
Мост идёт **через Objective-C**, а не напрямую в Swift, — отсюда все особенности.

| Kotlin | В Swift |
| --- | --- |
| `class`, `interface` | класс, протокол — работают привычно |
| `suspend fun` | функция с **completion handler**; в Swift доступна как `async` |
| `Flow` | **не мапится** — нужна обёртка |
| `sealed class` | обычные классы, `when` без `else` не проверяется компилятором Swift |
| `data class` | класс без структурного сравнения на стороне Swift |
| `Int`, `Boolean` в дженериках | боксируются в `KotlinInt`, `KotlinBoolean` |
| `List<T>`, `Map<K,V>` | `NSArray`, `NSDictionary` |
| Дженерики Kotlin | частично теряются: обобщённые типы Objective-C слабее |
| default-аргументы | **не переносятся** — в Swift придётся передавать все параметры |
| Имена классов | получают префикс (`SharedUser`), настраивается |

### suspend и Flow
`suspend`-функция вызывается из Swift как асинхронная — это работает из коробки:
```swift
let user = try await repository.loadUser(id: "42")
```
А вот `Flow` Objective-C не понимает. Варианты:
1. **SKIE** — плагин компилятора, автоматически превращающий `Flow` в `AsyncSequence`, а `sealed class` — в Swift `enum` с исчерпывающим `switch`. Сейчас это стандартный выбор.
2. **KMP-NativeCoroutines** — библиотека с тем же назначением.
3. Руками: обернуть `Flow` в класс с подпиской и функцией отмены.

```kotlin
// ручная обёртка, если без плагинов
class FlowWrapper<T>(private val flow: Flow<T>) {
    fun subscribe(onEach: (T) -> Unit, onComplete: () -> Unit): Cancellable { ... }
}
```

## Ошибки и исключения
Kotlin-исключение, вылетевшее в Swift, **роняет приложение**, если функция не помечена `@Throws`. Проверяемых исключений в Kotlin нет, поэтому граница модуля должна их не выпускать: возвращай **типизированный результат** (`Result<Data, Error>`) вместо бросания. Это ещё один аргумент за sealed-класс ошибок в общем коде. См. [[Classes. Exceptions]].

## Многопоточность и память
Историческая боль: до Kotlin 1.7.20 в Kotlin/Native действовала строгая модель памяти с **заморозкой** объектов (`freeze()`) и `InvalidMutabilityException` при попытке изменить объект из другого потока. Сейчас работает **новая модель памяти**, где ограничений на разделяемое состояние нет — код ведёт себя как на JVM.

Что осталось знать:
- В Kotlin/Native свой **сборщик мусора**, он не связан с ARC. Объекты, пришедшие из Swift, живут по правилам ARC, Kotlin-объекты — по правилам GC; **циклы ссылок между ними** GC не разрывает и приводят к утечкам.
- `Dispatchers.Main` на iOS — главная очередь GCD; `Dispatchers.IO` в Native отсутствует, используют `Dispatchers.Default`.

## Что обычно шарят на практике
Сначала выносят слои, где меньше всего платформенного: модели → валидация → сеть → репозитории → use cases. ViewModel-логику шарят реже: на iOS её всё равно оборачивают в `ObservableObject`, чтобы SwiftUI мог за ней наблюдать.

## Грабли
- **Размер бинарника** растёт: общий framework добавляет мегабайты; помогает `isStatic = true` и отключение лишних таргетов в debug.
- **Время сборки** iOS растёт из-за компиляции Kotlin/Native — особенно на CI без кэша.
- **Отладка**: точки останова в Kotlin из Xcode работают, но менее удобно; логи из общего кода нужно явно прокидывать.
- **Обновление Kotlin** тянет за собой обновление всех KMP-библиотек — версии связаны жёстче, чем на Android.
- **Default-аргументы и перегрузки** плохо переносятся: API общего модуля стоит проектировать «плоским», как будто его будет вызывать Objective-C.

## Вопросы-ловушки
- Почему `Flow` не виден из Swift? → мост идёт через Objective-C, который не знает про корутины; нужен SKIE или обёртка.
- Что будет с Kotlin-исключением в Swift? → без `@Throws` приложение упадёт; на границе лучше возвращать типизированный результат.
- Актуальна ли проблема с `freeze()`? → нет, новая модель памяти Kotlin/Native сняла ограничения на разделяемое состояние.
- Почему `Dispatchers.IO` нет на iOS? → в Kotlin/Native его не существует, используется `Dispatchers.Default`.
- Зачем XCFramework, если есть framework? → он содержит сборки под все архитектуры (устройство и симуляторы) в одном артефакте.
- Нужен ли iOS-разработчику Gradle? → нет, если CI отдаёт готовый XCFramework через SPM или CocoaPods.
