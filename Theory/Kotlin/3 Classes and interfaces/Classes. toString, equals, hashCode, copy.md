# toString, equals, hashCode, copy

Первые три метода есть **у любого объекта** — они объявлены в `Any` (аналог `Object` в Java) и потому доступны всегда. `copy` — не из `Any`, его генерирует компилятор для `data class`.

## toString()
Представление объекта строкой. По умолчанию возвращает `Имяпакета.ИмяКласса@hashCode` — больше `Any` про объект ничего не знает. Метод открыт для переопределения; `data class` генерирует его сам: `Person(name=Alice, age=25)`.

Зачем переопределять: логи и отладка. Грабли — не выводить в `toString` пароли, токены и персональные данные, они утекут в логи.

## equals(other: Any?) — оператор `==`
Отвечает на вопрос «эти два объекта равны?».
- **По умолчанию сравнивает ссылки**: равны, только если это один и тот же объект в памяти. Свойства не учитываются.
- Чтобы сравнивать **по полям**, `equals` переопределяют. Тогда `==` начинает работать по значению, а сравнить именно ссылки можно через `===` (его переопределить нельзя).

```kotlin
class Person(val name: String, val age: Int) {
    override fun equals(other: Any?): Boolean {
        if (this === other) return true          // быстрый выход: тот же объект
        if (other !is Person) return false       // заодно отсекает null
        return name == other.name && age == other.age
    }
}
```

### Контракт equals
Нарушишь — коллекции начнут вести себя непредсказуемо:
1. **Рефлексивность**: `a == a` всегда `true`.
2. **Симметричность**: если `a == b`, то `b == a`. Классическая поломка — сравнение с подклассом через `is` в одну сторону.
3. **Транзитивность**: `a == b` и `b == c` ⇒ `a == c`.
4. **Согласованность**: результат не меняется, пока не менялись поля.
5. `a == null` всегда `false`.

| Оператор / метод | Как работает | Что проверяет | Безопасен для `null` | Можно переопределить |
| --- | --- | --- | --- | --- |
| `==` | вызывает `equals()` под капотом (с null-проверкой) | значения | ✅ да | ✅ да |
| `equals()` | метод из `Any`; без переопределения работает как `===` | значения | ❌ нет (возможен NPE при явном вызове) | ✅ да |
| `===` | сравнение ссылок: тот же объект в памяти или нет | ссылку | ✅ да | ❌ нет |

## hashCode()
Представление объекта числом — «номер корзины», по которому хеш-структуры быстро находят кандидатов.
- По умолчанию считается от адреса объекта → у объектов с одинаковыми полями хеши **разные**.
- У `Int` `hashCode` совпадает со значением.

```kotlin
override fun hashCode(): Int = name.hashCode() * 31 + age
```
**Почему 31**: нечётное простое число даёт хорошее распределение (меньше коллизий), а `31 * x` JIT превращает в дешёвое `(x shl 5) - x`. Android Studio генерирует такой код автоматически (`Cmd+N` → `equals() and hashCode()`).

### Контракт hashCode
1. Равные по `equals` объекты **обязаны** иметь равный `hashCode`.
2. Обратное неверно: разные объекты могут дать одинаковый хеш — это **коллизия**, она допустима.
3. Пока поля не менялись — хеш стабилен.

**Переопределил `equals` — переопредели и `hashCode`.** Иначе получаешь двойственность: объекты «равны», но лежат в разных бакетах.

## Как это влияет на поиск в коллекциях

### List — только `equals`, O(n)
Линейный перебор с вызовом `equals` на каждом элементе.
```kotlin
data class Person(val name: String, val age: Int)

val list = listOf(Person("Alice", 25), Person("Bob", 30))
println(list.contains(Person("Alice", 25)))  // true — data class сгенерил equals
```

### HashSet / HashMap — `hashCode` + `equals`, в среднем O(1)
1. Берётся `hashCode()` → вычисляется индекс бакета.
2. Бакет пуст → элемента точно нет.
3. В бакете что-то есть (коллизия) → сравнение через `equals()`.

```kotlin
class Person(val name: String, val age: Int) {
    override fun equals(other: Any?) =
        other is Person && name == other.name && age == other.age
    // hashCode НЕ переопределён
}

val set = hashSetOf(Person("Alice", 25))
println(set.contains(Person("Alice", 25)))   // false! разные бакеты — до equals не дошло
```
Добавили `hashCode` из примера выше — станет `true`.

### TreeSet / TreeMap — `compareTo`, O(log n)
Красно-чёрное дерево, поиск по `compareTo()` из `Comparable`/`Comparator`. `equals` и `hashCode` **не используются вообще**.
```kotlin
class Person(val name: String, val age: Int) : Comparable<Person> {
    override fun compareTo(other: Person) = age - other.age   // сортировка по возрасту
}
```
Грабли: если `compareTo` смотрит не на все поля, разные люди одного возраста окажутся «одинаковыми» и второй просто не добавится.

| Коллекция | Как сравнивает | `equals` | `hashCode` | `compareTo` |
| --- | --- | --- | --- | --- |
| `List` | линейный поиск | ✅ | ❌ | ❌ |
| `HashSet` / `HashMap` | бакет + сравнение | ✅ | ✅ | ❌ |
| `TreeSet` / `TreeMap` | бинарный поиск в дереве | ❌ | ❌ | ✅ |

## copy() — только у data class
`copy` создаёт **новый** объект, копируя поля и подменяя те, что передали явно. Это основной способ «изменить» неизменяемое состояние (state в MVI, элементы списков).
```kotlin
data class Person(val name: String, val age: Int)

val alice = Person("Alice", 25)
val older = alice.copy(age = 26)     // Person(name=Alice, age=26), alice не изменился
```

Грабли:
- **Копия поверхностная (shallow)**: вложенные объекты не клонируются, копия и оригинал ссылаются на один и тот же список/объект. Для изменяемой вложенности это источник трудных багов — держи вложенные структуры тоже неизменяемыми.
- `copy`, `equals`, `hashCode` и `toString` у `data class` учитывают **только свойства первичного конструктора**. Поле, объявленное в теле класса, в копию не попадёт и на равенство не повлияет:
  ```kotlin
  data class User(val id: Int) {
      var nickname: String = ""      // НЕ участвует ни в copy, ни в equals
  }
  ```
- `copy` вызывает первичный конструктор, поэтому блоки `init` отрабатывают — валидация в `init` сработает и на копии.

## Вопросы-ловушки
- Переопределил `equals` без `hashCode` — что сломается? → `HashSet`/`HashMap`: объект «положили и не нашли».
- Что будет, если положить объект в `HashSet` и потом изменить поле, участвующее в `hashCode`? → элемент останется в старом бакете, `contains` вернёт `false`, а из `remove` он не удалится — утечка. Ключи хеш-структур должны быть неизменяемыми.
- Может ли `hashCode` совпасть у неравных объектов? → да, это коллизия, контракт её разрешает; недопустимо обратное — разный хеш у равных объектов.
- Почему `data class` не спасает автоматически? → он учитывает только поля первичного конструктора, остальное придётся писать руками.
