# Сортировки: что используется в Kotlin и как они устроены

## Что вызывается под капотом
| Что сортируем | Метод | Алгоритм |
| --- | --- | --- |
| `MutableList<T>` | `sort()` | **Timsort** (через `Collections.sort()`) |
| `List<T>` | `sorted()` | **Timsort** (возвращает копию) |
| `Array<T>` (объекты) | `sort()` | **Timsort** |
| `IntArray`, `DoubleArray` и другие примитивные | `sort()` | **Dual-Pivot QuickSort** |

Почему разные алгоритмы — важный вопрос на собеседовании. Для **объектов** нужна **устойчивость** (равные элементы сохраняют исходный порядок) — её даёт Timsort. Для **примитивов** устойчивость бессмысленна: два одинаковых `Int` неразличимы, поэтому берут более быстрый по памяти и константам Dual-Pivot QuickSort, который сортирует на месте.

## Timsort — гибрид слияния и вставок
Придуман для Python, затем перенесён в Java. Идея — использовать то, что реальные данные **почти отсортированы**:
1. Массив разбивается на **runs** — уже упорядоченные (по возрастанию или убыванию) участки; убывающие переворачиваются.
2. Короткие участки досортировываются **сортировкой вставками** — на малых n она быстрее всего.
3. Полученные runs **сливаются** попарно, как в merge sort, с эвристикой *galloping* для случая, когда один run целиком меньше другого.

Результат: **O(n log n)** в худшем случае и близко к **O(n)** на почти отсортированных данных. Плата — O(n) дополнительной памяти.

## Основные алгоритмы
| Алгоритм | Среднее | Худшее | Память | Устойчив | Идея |
| --- | --- | --- | --- | --- | --- |
| **Selection** | O(n²) | O(n²) | O(1) | нет | искать минимум и ставить на место. См. [[Selection sort O(n^2)]] |
| **Bubble** | O(n²) | O(n²) | O(1) | да | «всплывать» соседними обменами |
| **Insertion** | O(n²) | O(n²) | O(1) | да | вставлять элемент в готовую часть; **O(n)** на почти отсортированном |
| **Merge** | O(n log n) | O(n log n) | **O(n)** | да | делить пополам и сливать |
| **Quick** | O(n log n) | **O(n²)** | O(log n) | нет | разделение относительно опорного |
| **Heap** | O(n log n) | O(n log n) | O(1) | нет | построить кучу и извлекать максимум. См. [[5. Priority queue]] |
| **Timsort** | O(n log n) | O(n log n) | O(n) | да | merge + insertion по готовым участкам |
| **Counting/Radix** | O(n + k) | O(n + k) | O(k) | да | не сравнением, а раскладкой по «корзинам» |

**Нижняя граница**: любая сортировка **сравнениями** не может быть быстрее O(n log n) — это доказанный предел. Counting и radix обходят его лишь потому, что не сравнивают элементы, а используют их значения как индексы; за это платят ограничением на диапазон данных.

## Quicksort: почему O(n²) в худшем случае
Опорный элемент делит массив на части. Если он каждый раз оказывается минимумом или максимумом (например, массив уже отсортирован, а опорный берётся первым), деления пополам не происходит: получается n уровней вместо log n. Лечится выбором опорного — случайным, «медиана из трёх» или двумя опорными (Dual-Pivot).

## Зачем нужна устойчивость
Устойчивая сортировка сохраняет относительный порядок равных элементов. Это позволяет сортировать **по нескольким критериям последовательно**:
```kotlin
val result = users
    .sortedBy { it.name }     // сначала по имени
    .sortedBy { it.age }      // затем по возрасту: внутри возраста имена остались упорядоченными
```
С неустойчивой сортировкой такой приём не работает. В Kotlin обычно пишут явно:
```kotlin
users.sortedWith(compareBy({ it.age }, { it.name }))
```

## Поиск: что делает find
`find { }` — это **линейный поиск** O(n), без всякой магии:
```kotlin
inline fun <T> Iterable<T>.find(predicate: (T) -> Boolean): T? {
    for (element in this) if (predicate(element)) return element
    return null
}
```
Он перебирает элементы по порядку и останавливается на первом совпадении — **даже если коллекция отсортирована**. Когда поиск частый, нужна другая структура:
| Способ | Сложность | Условие |
| --- | --- | --- |
| `find { }`, `contains` у List | O(n) | ничего не требует |
| `HashSet.contains`, `HashMap.containsKey` | O(1) в среднем | хороший `hashCode` |
| `binarySearch` | O(log n) | отсортированный список/массив |

См. [[Linear search O(n)]], [[Binary search O(log n)]], [[Collections. Overview]].

## Вопросы-ловушки
- Почему для примитивов и объектов в JDK разные сортировки? → объектам нужна устойчивость (Timsort), примитивам она не нужна, зато важны скорость и память (Dual-Pivot QuickSort).
- Может ли сортировка быть быстрее O(n log n)? → только не основанная на сравнениях (counting, radix) и при ограниченном диапазоне значений.
- Когда quicksort деградирует до O(n²)? → при неудачном выборе опорного, например на уже отсортированных данных.
- Зачем устойчивость на практике? → многокритериальная сортировка последовательными проходами.
- Чем Timsort лучше обычного merge sort? → использует уже упорядоченные участки: на почти отсортированных данных работает почти за O(n).
