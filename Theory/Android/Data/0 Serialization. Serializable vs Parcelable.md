# Сериализация и десериализация

**Сериализация** – преобразование объектов в строки.  
**Десериализация** – преобразование строк или набора байт в объекты.  
## JSON (JavaScript Object Notation)

JSON – представление любых объектов в виде пары *ключ-значение*.  
Наиболее распространенный формат представления объекта в строку.

```json
[  
  {  
    "id": 1,  
    "name": "Ivan",  
    "email": "Ivan@mail.ru",  
    "registered_at": "11.01.2021"  
  },  
  {  
    "id": 2,  
    "name": "Maria",  
    "email": "Maria@mail.ru",  
    "registered_at": "11.01.2022"  
  }  
]
```

`kotlinx.serialization` – библиотека для работы с JSON

### Использование:

1. Подключить библиотеку.
2. Пометить класс аннотацией `@Serializable` – позволяет сгенерировать код для сериализации и десериализации данного объекта.
3. Если имя поля класса не совпадает с именем в файле ключа json, можно пометить поле аннотацией @SerialName. В идеале добавлять эти аннотации для всех полей для ясности и читаемости+после обфускации(кодирования имен кода) имена ключей и переменных будут отличаться, и код перестанет работать

```kotlin
@Serializable  
data class User(  
    @SerialName("id") val id: Int,  
    @SerialName("name") val name: String,  
    @SerialName("email") val email: String,  
    @SerialName("registered_at") val registeredAt: String  
)  
  
fun serializeUser(user: User): String {  
    return Json.encodeToString(user)  
}  
  
fun deserializeUser(json: String): User {  
    return Json.decodeFromString<User>(json)  
}
```

## Serializable vs Parcelable

Оба интерфейса решают одну задачу — превратить объект в набор байт и обратно, — но предназначены для разного.

### Serializable
Стандартный интерфейс Java, **маркерный**: методов в нём нет, реализовать ничего не нужно.
```kotlin
data class User(val id: Int, val name: String) : java.io.Serializable
```
Всю работу делает JVM через **рефлексию** — механизм, позволяющий во время выполнения разбирать структуру класса: поля, типы, значения. Отсюда и минусы: рефлексия медленная и порождает много временных объектов, а значит — работу GC и подтормаживания UI.

Детали, о которых спрашивают:
- `serialVersionUID` — версия схемы класса. Если не задать явно, JVM вычислит её из структуры, и после малейшего изменения класса старые сохранённые данные перестанут читаться (`InvalidClassException`).
- `transient`-поля не сериализуются.
- `enum` реализуют `Serializable` неявно.

### Parcelable
Android-специфичный интерфейс: объект сам описывает, как записаться в **`Parcel`** — буфер для передачи через Binder. Рефлексии нет, поля пишутся напрямую в нужном порядке, поэтому это в разы быстрее и почти не мусорит в памяти.

Руками писать `writeToParcel`/`CREATOR` не нужно — плагин **`kotlin-parcelize`** генерирует код по аннотации:
```kotlin
// build.gradle.kts: plugins { id("kotlin-parcelize") }

@Parcelize
data class User(val id: Int, val name: String) : Parcelable
```

| Характеристика | Serializable | Parcelable (`@Parcelize`) |
| --- | --- | --- |
| Происхождение | стандартный интерфейс Java | Android-специфичный |
| Реализация | автоматически, через рефлексию | генерируется плагином (или вручную) |
| Производительность | медленнее, создаёт много мусора | быстрее, без рефлексии |
| Где применять | сохранение в файл, обмен с не-Android кодом | передача внутри Android: `Intent`, `Bundle`, IPC |

### Главная ловушка Parcelable
**`Parcel` — не формат хранения.** Его внутреннее представление зависит от версии Android и может измениться между релизами. Записывать Parcel в файл или базу — ошибка: после обновления системы данные не прочитаются. Parcel живёт ровно столько, сколько идёт передача.

Для долговременного хранения — JSON (`kotlinx.serialization`), Room или DataStore.

## Что выбирать
- Передача между Activity/Fragment/процессами → **Parcelable**.
- Сохранение на диск, кэш, сеть → **JSON через `kotlinx.serialization`**.
- `Serializable` — только когда объект приходит из чужой Java-библиотеки и переделывать его нет смысла.

## Вопросы-ловушки
- Почему Parcelable быстрее? → нет рефлексии: код сериализации сгенерирован заранее, и он не создаёт лишних объектов.
- Можно ли сохранить Parcelable в файл? → нельзя: формат Parcel не стабилен между версиями Android.
- Зачем `serialVersionUID`? → зафиксировать версию схемы, иначе изменение класса ломает чтение старых данных.
- Что произойдёт, если положить в `Bundle` объект, не реализующий ни один из интерфейсов? → `RuntimeException` при упаковке в Parcel. См. [[Bundle]].
- `@Parcelize` работает не только с `data class`? → да, с любым классом, но все поля первичного конструктора должны быть сериализуемы (для нестандартных типов — свой `Parceler`).
