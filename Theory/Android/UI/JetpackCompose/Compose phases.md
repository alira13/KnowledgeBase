# Фазы кадра в Compose

Каждый кадр Compose проходит **три фазы**. Понимание, в какой фазе читается состояние, — главный инструмент оптимизации: часто задачу решает не уменьшение работы, а её перенос в более позднюю фазу.

| Фаза | Отвечает на вопрос | Что происходит |
| --- | --- | --- |
| **1. Composition** | **что** показывать | выполняются composable-функции, строится (или обновляется) дерево UI |
| **2. Layout** | **где** это расположить | каждый узел измеряется и размещается: measure + place |
| **3. Drawing** | **как** это нарисовать | узлы рисуют себя на Canvas |

Это прямой аналог `measure` → `layout` → `draw` во View-системе, но с отдельной фазой построения дерева вместо inflate. См. [[View. UI rendering stages]].

## Layout: почему один проход
В отличие от View, где вложенные `measure` могли вызываться многократно (и порождать экспоненциальную сложность при глубокой вложенности), в Compose действует правило: **каждого ребёнка можно измерить ровно один раз** за проход. Попытка измерить дважды — исключение.

Отсюда важное следствие: глубина иерархии в Compose стоит дёшево, вложенные layout'ы не приводят к тем проблемам, ради которых во View-системе изобретали `ConstraintLayout`.

Механика фазы:
1. Родитель передаёт ребёнку **constraints** (мин/макс ширина и высота).
2. Ребёнок измеряет себя и своих детей, сообщает размер.
3. Родитель размещает детей по координатам.

Когда нужно узнать размер до размещения, есть `SubcomposeLayout` (на нём построен `BoxWithConstraints`) — он делает **композицию внутри фазы layout**, за что и платит производительностью.

## Ключевая идея: читай состояние как можно позже
Compose отслеживает, **в какой фазе** прочитано значение `State`, и перезапускает только эту фазу и последующие:

| Где прочитано | Что перезапустится |
| --- | --- |
| в теле composable | composition → layout → drawing |
| в лямбде layout-модификатора | layout → drawing |
| в лямбде drawing-модификатора | только drawing |

Отсюда практический приём — передавать **лямбду**, а не значение:
```kotlin
// плохо: offset читается в composition → рекомпозиция на каждом кадре анимации
Box(Modifier.offset(x = animatedOffset.dp))

// хорошо: значение читается в фазе layout → композиция не перезапускается
Box(Modifier.offset { IntOffset(animatedOffset.roundToPx(), 0) })
```
```kotlin
// плохо
Box(Modifier.background(animatedColor))

// хорошо: чтение в фазе drawing
Box(Modifier.drawBehind { drawRect(animatedColor) })
```
Для анимаций это разница между «пересобирать дерево 60 раз в секунду» и «только перерисовывать».

То же относится к `graphicsLayer { }` — изменения alpha, scale, rotation внутри него не трогают ни композицию, ни layout.

## Что попадает в какую фазу
- **Composition**: `remember`, вызовы composable, чтение `state.value` в теле.
- **Layout**: `Modifier.offset { }`, `padding` с лямбдой, `layout { }`, `onGloballyPositioned`.
- **Drawing**: `Modifier.drawBehind { }`, `drawWithContent { }`, `graphicsLayer { }`, `Canvas`.

## Как диагностировать
- **Layout Inspector** — счётчики рекомпозиций и пропусков по каждому composable.
- **Compose compiler metrics** — какие функции skippable/restartable.
- Правило проверки: если во время анимации счётчик рекомпозиций растёт — состояние читается слишком рано.

## Вопросы-ловушки
- Сколько фаз в кадре Compose и в каком порядке? → composition → layout → drawing.
- Почему `Modifier.offset { }` эффективнее `Modifier.offset(x)`? → лямбда читает состояние в фазе layout, поэтому композиция не перезапускается.
- Может ли Compose измерить ребёнка дважды? → нет, это ошибка; обход — `SubcomposeLayout`, но он дороже.
- Обязательно ли рекомпозиция ведёт к перерисовке? → нет: если результат не изменился, поздние фазы могут быть пропущены; и наоборот — перерисовка бывает без рекомпозиции.
- Почему глубокая вложенность в Compose не так страшна, как во View? → один проход измерения вместо возможных повторных.
