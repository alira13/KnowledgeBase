
1. ==**Что такое JetpackCompose?**==
JetpackCompose - технология от Google для создания UI без файлов верстки
С Jetpack Compose создание UI сводится к написанию функций, которые описывают, как интерфейс должен выглядеть и реагировать на изменения. Все это реализуется в Kotlin, без использования XML.
Классический подход:
 - пошагово вызываем функции, описывающие, как компоненты должны изменяться
 Compose:
- на состояниях. То есть это слепок экрана в момент времени, и чтобы его изменить, нужно изменить состояние экрана.
- возможности вызывать отдельные методы и менять отдельные свойства у нас просто нет. Нам нужно сразу задать финальное состояние, поэтому единственный способ обновить любой компонент на экране — вызвать ту же composable-функцию с новыми аргументами. Эти аргументы представляют состояние пользовательского интерфейса. Каждый раз, когда состояние обновляется, происходит вызов compose-функции с новыми входными параметрами. Этот процесс называется «рекомпозиция»,

2. ==**Зачем его сделали?**==
  - упростить процесс разработки класc view - это god-object с 30тыс строк+нужно знать xml
  - сделать его более гибким 
 - эффективным
 - соответствующим современным тенденциям в создании UI. Jetpack compose+Multiplatform
 
Старый подход
1. создаем файлы верстки на языке xml из элементов-наследников класса View
2. `setContentView(R.layout.activity_main)` — связывает XML-файл `activity_main.xml` с текущей `Activity`. Этот файл находится в папке `res/layout`.
- `R.layout.activity_main` — это ссылка на ресурс XML, сгенерированная автоматически в классе `R` (ресурсы приложения).
- После вызова `setContentView()`, элементы интерфейса, определенные в XML, становятся доступными для взаимодействия с помощью их ID.
2. работаем с view из кода, устанавливаем слушатели, значения текстов и тд. 
Решение проблем старого подхода: 
 - нужно знать кроме Kotlin еще xml. В Compose только kotlin
 - класc view - это god-object с 30тыс строк. Сложно разобраться и поддерживать. В Jetpack Compose  отказались от использования системы иерархии классов наследованных от view. Все построено на декларативном подходе и функциях.

##### Основные причины создания Jetpack Compose:

1. **Устранение сложностей работы с XML**  
    Традиционный подход к разработке UI в Android разделяет логику (написанную в Kotlin/Java) и верстку (XML). Это часто приводит к избыточности кода, сложности в управлении состоянием и синхронизации между UI и логикой.  
    В Compose весь UI описывается в Kotlin, что устраняет необходимость работы с XML и делает код более читаемым и лаконичным.
    
2. **Функциональный подход к разработке UI**  
    В традиционном подходе `View`-система требует ручного управления состоянием и сложной логики для обновления интерфейса. Compose основан на **декларативной модели**, где вы просто описываете, как должен выглядеть UI в зависимости от состояния, а сам Compose автоматически обновляет интерфейс при изменении этого состояния.
    
3. **Меньше кода и больше читаемости**  
    Compose позволяет создавать сложные пользовательские интерфейсы с меньшим количеством кода. Это достигается благодаря мощным DSL (Domain Specific Language) конструкциям в Kotlin.
    
    **Пример XML и традиционного подхода:**
    
    ```xml
    <!-- activity_main.xml -->
    <TextView
        android:id="@+id/textView"
        android:layout_width="wrap_content"
        android:layout_height="wrap_content"
        android:text="Hello, World!" />
    ```
    
    ```kotlin
    // MainActivity.kt
    val textView = findViewById<TextView>(R.id.textView)
    textView.text = "Hello, Compose!"
    ```
    
    **Compose-подход:**
    
    ```kotlin
    @Composable
    fun Greeting() {
        Text(text = "Hello, Compose!")
    }
    ```
    
4. **Управление состоянием**  
    Jetpack Compose предлагает встроенные инструменты для управления состоянием. Это делает обработку UI-состояний более предсказуемой и интуитивной, устраняя необходимость ручного управления обновлениями `View`.
    
5. **Унификация кода**  
    Compose позволяет использовать один и тот же код для описания интерфейса, как для Android-приложений, так и для других платформ (например, с помощью Compose Multiplatform). Это особенно полезно для команд, работающих над многоплатформенными проектами.
    
6. **Модернизация и производительность**  
    Традиционная `View`-система Android была создана более 10 лет назад, и её архитектура не всегда хорошо соответствует требованиям современных приложений. Compose был создан с учётом современных подходов, что обеспечивает:
    
    - Лучшую производительность.
    - Упрощённое тестирование.
    - Возможность быстрой адаптации новых функций.
7. **Гибкость и кастомизация**  
    Создание кастомных компонентов в традиционной `View`-системе требует написания пользовательских классов, которые часто сложны для поддержки. В Compose кастомизация компонентов проще и осуществляется декларативно.
    
8. **Интеграция с другими инструментами Jetpack**  
    Compose полностью совместим с другими библиотеками Jetpack, такими как Navigation, LiveData, ViewModel, и Room, что делает его идеальным выбором для современных Android-приложений.

3. И как на нем сделать UI?
	1. Включите поддержку Jetpack Compose в `build.gradle`
```
android {
    buildFeatures {
        compose true
    }
    composeOptions {
        kotlinCompilerExtensionVersion "1.x.x" // Укажите актуальную версию
    }
}

dependencies {
    implementation "androidx.compose.ui:ui:1.x.x"
    implementation "androidx.compose.material:material:1.x.x"
    implementation "androidx.compose.ui:ui-tooling-preview:1.x.x"
}
```

 2. Создать Composable - функцию. В compose все основано на функциях и передаче в них ИМЕННОВАННЫХ параметров. 
	 - также начинаются с ключевого слова fun
	 - помечены аннотацией @Composable. @Composable - значит что метод используется в отрисовке UI. 
	 - именются: с маленькой буквы начинаются функции, обозначающие состояние, с большой буквы начинаются функции обозначающие действие
	 - comp-функции могут вызываться только внутри comp-функций, а не в любом месте

3. Укажите `Composable` в `setContent()` внутри Activity в onCreate()
@Preview - используется для предпросмотра Compose-функции. Но может быть использована только для функциий без аргументов. Выход-создать функцию без аргументов, пометить Preview и оттуда вызвать нужную функцию

Jetpack Compose предлагает множество компонентов (или **композаблов**), которые можно использовать для создания UI. Они охватывают как базовые элементы, такие как текст и кнопки, так и сложные структуры, такие как списки и анимации.

### 1. **Контейнеры для компоновки**

Контейнеры управляют расположением дочерних компонентов:

- **`Column`**  - аналог LinearLayout orientation = vertical
    Располагает элементы вертикально.
    
    ```kotlin
    Column {
        Text("Item 1")
        Text("Item 2")
    }
    ```
    
- **`Row`**  
    Располагает элементы горизонтально. аналог LinearLayout orientation = horizontal
    
    ```kotlin
    Row {
        Text("Item 1")
        Text("Item 2")
    }
    ```
    
- **`Box`**  

    Коробочка с каким-то содержимым. Накладывает элементы друг на друга.
    
    ```kotlin
    Box {
        Image(/* ... */)
        Text("Overlayed text")
    }
    ```
    
- **`LazyColumn`**  
    Вертикальный список с поддержкой больших объемов данных.
    
    ```kotlin
    LazyColumn {
        items(100) { index ->
            Text("Item $index")
        }
    }
    ```
    
- **`LazyRow`**  
    Горизонтальный список с ленивой загрузкой.
    
    ```kotlin
    LazyRow {
        items(10) { index ->
            Text("Row $index")
        }
    }
    ```

**==А вот теперь хочу, чтобы при клике на кнопку поменялась надпись, что сделать надо?
==**
Если мы просто создадим обычную переменную и в onClick начнем изменять, то на экране ничего не произойдет, так как никто не сообщает Composable-фцнкции, что состояние изменилось и ей нужно перерисоваться.

Чтобы создать объект с изменяемым состоянием, а не простую типизированную переменную, можно воспользоваться встроенными в compose функциями: `remember` и `mutableStateOf<>()`.

- `remember` позволяет сохранять в памяти объекты после рекомпозиции.
- `mutableStateOf` — специализированный объект Compose, который может отслеживаться compose-функциями. Его изменение вызовет рекомпозицию.

Compose-функции описывают состояние экрана. То есть чтобы мы увидели изменения на экране, допустим при клике на кнопку изменился текст, нужно изменить состояние экрана.
Чтобы изменить состояние, нужно повторно вызвать compose-функцию, но с уже новыми параметрами. Но перерисовывать все элементы интерфейса при изменении состояния 1 элемента вроде как не хочется. И compose позволяет это сделать.

Для изменения состояния интерфейса в Jetpack Compose:
1. Мы создаем переменную состояния с помощью `mutableStateOf`
2. Чтобы state сохранился между рекомпозициями, необходимо использовать функцию remember
3. Привяжите её к UI-компонентам.Если хотим получить из state значение, используем поле value, также и чтобы положить туда значение
4. Меняйте состояние при взаимодействии, чтобы UI обновлялся автоматически.
5. При необходимости используйте `ViewModel` для более сложных экранов.
Если нам нужно, чтобы после рекомпозиции какой-то элемент не отображался, мы просто не должны вызывать функцию отрисовки этого элемента.

Если нам нужно, чтобы composable-функция зависела от какого-то состояния, то при изменении этого состояния она будет вызвана снова - произойдет рекомпозиция.

Если мы хотим, чтобы какой-то элемент не был видим на экране или не перерисовался, нам просто не нужно вызывать его composable-функцию

Stateless-composable функция - функция, которая не управляет своим состоянием сама. Она лишь принимает на вход управляющую функцию
StateFull-composable функция - функция, которая управляет своим состоянием сама

**Рекомпозиция** в Jetpack Compose — это процесс повторного вызова функций, аннотированных как `@Composable`, чтобы обновить пользовательский интерфейс на основе изменений данных (состояния). Compose автоматически управляет этим процессом, обеспечивая обновление только тех частей интерфейса, которые изменились.


### Как работает рекомпозиция?

1. **Обнаружение изменений состояния**  
    Когда состояние (например, `mutableStateOf`) изменяется, Compose понимает, что интерфейс, зависящий от этого состояния, нуждается в обновлении.
    
2. **Повторный вызов `@Composable` функции**  
    Compose повторно вызывает только те `@Composable` функции, которые зависят от изменившегося состояния. Это похоже на перерисовку части экрана.
    
3. **Оптимизация производительности**  
    Jetpack Compose обновляет только изменённые части интерфейса, не трогая остальной UI, что делает рекомпозицию эффективной.
    
### Пример рекомпозиции

Вот пример, демонстрирующий, как происходит рекомпозиция:

```kotlin
@Composable
fun Counter() {
    var count by remember { mutableStateOf(0) }

    Column {
        Text(text = "Count: $count") // Этот текст обновится при изменении `count`
        Button(onClick = { count++ }) {
            Text("Increase")
        }
    }
}
```

1. Когда пользователь нажимает кнопку, состояние `count` изменяется.
2. Compose обнаруживает изменение `count` и вызывает `Text(text = "Count: $count")` снова.
3. Другие части интерфейса (например, кнопка) не затрагиваются.

---

### Ключевые особенности рекомпозиции

1. **Локальность**  
    Только функции, зависящие от изменившегося состояния, подвергаются рекомпозиции. Остальные части интерфейса остаются неизменными.
    
2. **Идемпотентность**  
    `@Composable` функции можно безопасно вызывать многократно. Они не должны изменять состояние напрямую (избегайте побочных эффектов).
    
3. **Управление состоянием**  
    Рекомпозиция инициируется только при изменении состояния. Если состояние не изменилось, функция не будет вызвана снова.

### Когда происходит рекомпозиция?

Рекомпозиция происходит при:

- Изменении состояния (`mutableStateOf`, `LiveData`, `Flow`, и т. д.).
- Повороте экрана или изменении конфигурации.
- Вызове `setContent` в Activity или Fragment.

### Как минимизировать избыточную рекомпозицию?

1. **Используйте `remember`**  
    Чтобы сохранить значения между рекомпозициями.
    
    ```kotlin
    val text = remember { "Hello, Compose!" }
    ```
    
2. **Разделяйте функции**  
    Разделяйте `@Composable` функции на небольшие части, чтобы минимизировать объем рекомпозиции.
    
3. **Используйте `derivedStateOf`**  
    Для вычисления производных состояний на основе другого состояния.
    
4. **Оптимизируйте списки с помощью `LazyColumn` и `key`**
    
    ```kotlin
    LazyColumn {
        items(itemsList, key = { it.id }) { item ->
            Text(item.name)
        }
    }
    ```

==**Какие presentation-паттерны используются для организации кода JC**==
Compose-функции можно разделить на:
- Компоненты **с состоянием** (`stateful`) управляют своим состоянием внутри функции.
- Компоненты **без состояния** (`stateless`) принимают состояние через параметры и сообщают об изменениях через лямбды.

Для сложных экранов рекомендуется использовать presentation-паттерны. Это улучшает разделение логики и UI.

Наиболее популярные presentation-паттерны для Jetpack Compose:
1. **MVVM** — простой и удобный, часто используется в связке с `StateFlow` или `LiveData`.
2. **MVI** — односторонний поток данных, удобен для сложного состояния и исторического трекинга.
3. **Redux** — строгий подход с одним источником истины.


**MVVM: Вынос состояния во ViewModel (при необходимости)**

Пример: использование `ViewModel`.
```
import androidx.lifecycle.viewmodel.compose.viewModel

class MyViewModel : ViewModel() {
    private val _text = MutableLiveData("Hello, ViewModel!")
    val text: LiveData<String> = _text

    fun updateText(newText: String) {
        _text.value = newText
    }
}

@Composable
fun MyScreen(viewModel: MyViewModel = viewModel()) {
    val text by viewModel.text.observeAsState("")

    Column {
        Text(text = text)
        Button(onClick = { viewModel.updateText("Updated from ViewModel!") }) {
            Text("Update")
        }
    }
}

```


Вынос управления состоянием во **ViewModel** — это важный шаг для отделения логики от пользовательского интерфейса (UI) и повышения тестируемости. Вот пошаговый процесс, как это сделать:

---

### 1. **Создайте ViewModel**

ViewModel отвечает за хранение состояния и управление логикой. Создайте класс, унаследованный от `ViewModel`.

Пример:

```kotlin
class CounterViewModel : ViewModel() {
    // Здесь будет управление состоянием
}
```

---

### 2. **Определите состояние UI**

Опишите состояние интерфейса в виде:

- **Простого типа данных** (например, `Int`, `String`).
- **Класса состояния** (`data class`) для более сложных интерфейсов.

Пример:

```kotlin
data class CounterState(
    val count: Int = 0
)
```

---

### 3. **Добавьте StateFlow или LiveData**

ViewModel должна предоставлять данные для UI. Используйте:

- **StateFlow** (рекомендуемый подход для Jetpack Compose).
- **LiveData** (если вы хотите совместимость со старыми фреймворками).

Пример с `StateFlow`:

```kotlin
class CounterViewModel : ViewModel() {
    private val _uiState = MutableStateFlow(CounterState())
    val uiState: StateFlow<CounterState> = _uiState

    fun increment() {
        _uiState.value = _uiState.value.copy(count = _uiState.value.count + 1)
    }
}
```

---

### 4. **Подключите ViewModel к Compose**

В `@Composable` функции создайте или передайте ViewModel. Используйте функцию `viewModel()` для автоматического создания ViewModel.

Пример:

```kotlin
@Composable
fun CounterScreen(viewModel: CounterViewModel = viewModel()) {
    val state by viewModel.uiState.collectAsState()

    Column {
        Text(text = "Count: ${state.count}")
        Button(onClick = { viewModel.increment() }) {
            Text("Increment")
        }
    }
}
```

---

### 5. **Перенесите управление состоянием во ViewModel**

Если ранее управление состоянием было в Compose, перенесите его в ViewModel:

- Замените `remember` или `mutableStateOf` на `StateFlow` или `LiveData`.
- Переместите всю бизнес-логику в методы ViewModel.
По большому счёту, фреймворк compose предлагает набор встроенных функций-конвертеров, которые преобразуют один тип изменяемого состояния в другой ( `State<T>`), который уже используют все composable-функции.

- `Flow<T>.collectAsStateWithLifecycle()` преобразует из `Flow<T>` в `State<T>` с зависимостью на жизненный цикл. Это позволяет, например, останавливать вычисления при «уничтожении» экрана или приложения.
    
- `LiveData<T>.observeAsState()` аналогичным образом преобразует `LiveData<T>` в `State<T>` и изначально зависит от жизненного цикла.

**До (состояние в Compose):**

```kotlin
@Composable
fun CounterScreen() {
    var count by remember { mutableStateOf(0) }

    Column {
        Text(text = "Count: $count")
        Button(onClick = { count++ }) {
            Text("Increment")
        }
    }
}
```

**После (состояние во ViewModel):**

```kotlin
class CounterViewModel : ViewModel() {
    private val _count = MutableStateFlow(0)
    val count: StateFlow<Int> = _count

    fun increment() {
        _count.value++
    }
}

@Composable
fun CounterScreen(viewModel: CounterViewModel = viewModel()) {
    val count by viewModel.count.collectAsState()

    Column {
        Text(text = "Count: $count")
        Button(onClick = { viewModel.increment() }) {
            Text("Increment")
        }
    }
}
```

---

### 6. **Управление сложным состоянием**

Если состояние сложное (например, содержит несколько параметров), используйте `data class` для представления состояния и обновляйте его с помощью `copy()`.

Пример:

```kotlin
data class UiState(
    val count: Int = 0,
    val isLoading: Boolean = false
)

class MyViewModel : ViewModel() {
    private val _uiState = MutableStateFlow(UiState())
    val uiState: StateFlow<UiState> = _uiState

    fun increment() {
        _uiState.value = _uiState.value.copy(count = _uiState.value.count + 1)
    }

    fun setLoading(loading: Boolean) {
        _uiState.value = _uiState.value.copy(isLoading = loading)
    }
}
```

---

### 7. **Используйте ViewModel с навигацией**

Если экран связан с навигацией, создавайте ViewModel с помощью `hiltViewModel()` или `NavBackStackEntry`.

Пример с `hiltViewModel` (Dagger Hilt):

```kotlin
@Composable
fun CounterScreen(viewModel: CounterViewModel = hiltViewModel()) {
    val state by viewModel.uiState.collectAsState()

    Column {
        Text(text = "Count: ${state.count}")
        Button(onClick = { viewModel.increment() }) {
            Text("Increment")
        }
    }
}
```

---

### 8. **Добавьте тестирование ViewModel**

Вынося состояние во ViewModel, вы упрощаете тестирование. Напишите юнит-тесты для проверки бизнес-логики.

Пример теста:

```kotlin
class CounterViewModelTest {
    @Test
    fun testIncrement() {
        val viewModel = CounterViewModel()

        viewModel.increment()

        assertEquals(1, viewModel.uiState.value.count)
    }
}
```

---

### Итоговые шаги:

1. Создайте ViewModel и опишите состояние (`StateFlow`, `LiveData`, `data class`).
2. Храните состояние в ViewModel, используя `MutableStateFlow` или `MutableLiveData`.
3. Перенесите бизнес-логику в методы ViewModel.
4. Подключите ViewModel к UI через `viewModel()` или `hiltViewModel()`.
5. В `@Composable` функции используйте `collectAsState()` для получения состояния из ViewModel.
6. Организуйте тестирование ViewModel.

Этот подход упрощает поддержку приложения и обеспечивает лучшее разделение ответственности.

Жизненный цикл Compose
Каждый компонент проходит несколько стадий
- **Вход в композицию (Entering the Composition):** Когда composable-функция вызывается впервые, Compose отслеживает её и добавляет в композицию — структуру, описывающую текущий UI. В стартовом проекте вы объявляете композицию внутри setContent() в MainActivity.После запуска приложения ваши Composable объекты входят в композицию, объявленную в MainScreen(), которая затем вызывает подобъекты и тд всеми составными объектами. Но на фазу рекомпозиции компоненты не перейдут, если не будет mutableState
    
- **Рекомпозиция (Recomposition):** При изменении состояния, влияющего на UI, Compose повторно выполняет необходимые composable-функции, обновляя отображаемый интерфейс.
- **Выход из композиции (Leaving the Composition):** Когда composable-функция больше не требуется (например, при удалении из UI), Compose удаляет её из композиции, освобождая ресурсы.

Почему нужно следить за рекомпозицией?
Потому что это может привести к ухудшению производительности приложения. Когда мы будем перерисовывать весь экран вместо одного текстового поля.

Случаи, когда происходит рекомпозиция:

### 1. **Изменение состояния**

- **Изменение состояния внутри composable-функции** (mutable state):  
    Например, если внутри composable-функции изменяется значение переменной `State` или `MutableState`, Compose инициирует её повторное выполнение, чтобы отобразить обновлённое состояние UI.
    
    ```kotlin
    var counter by remember { mutableStateOf(0) }
    Button(onClick = { counter++ }) {
        Text("Counter: $counter")
    }
    ```
    
- **Коллекция изменений в `State` объектов** (e.g., `State` или `MutableState`):  
    Когда Observable состояние обновляется (например, с помощью `LiveData` или `StateFlow`).

### 2. **Изменение `remember` объектов**

- **Обновление объектов `remember`**:  
    Если в composable-функции используются `remember` для хранения состояния, то любая новая ссылка, передаваемая в `remember` или любые зависимости из `remember` изменяются, инициируют рекомпозицию.
    
    ```kotlin
    val counter by remember { mutableStateOf(0) }
    Button(onClick = { counter++ }) {
        Text("Counter: $counter")
    }
    ```
    

### 3. **Изменение параметров (props) composable-функций**

- **Изменение входных параметров** (параметры composable-функций):  
    При изменении входных параметров, которые влияют на поведение или отображение composable-функции, происходит рекомпозиция.
    
    ```kotlin
    @Composable
    fun Greeting(name: String) {
        Text("Hello, $name!")
    }
    
    @Preview
    @Composable
    fun PreviewGreeting() {
        Greeting(name = "World")
    }
    ```
    

### 4. **Изменение системных факторов**

- **Lifecycle событий**:  
    Например, изменение состояния жизненного цикла компонента, такого как активация или деактивация компонента, вызывает рекомпозицию. Например, если активность становится невидимой (`onDispose` в композите).
- **Orientation change**:  
    Поворот экрана вызывает рекомпозицию, так как создаются новые экземпляры composable-функций.

### 5. **Изменение параметров при параметризации компонентов**

- **Key параметризация (`key`)**:  
    Если применён ключ (`key`) к composable-функции, даже если входные параметры не изменяются, компоненты пересоздаются.
    
    ```kotlin
    @Composable
    fun MyItem(key: String) {
        Text("Item: $key")
    }
    ```
    

### 6. **Запросы на повторную загрузку данных (LaunchedEffect или SideEffects)**

- **Side effects и LaunchedEffect**:  
    Если компонент использует `LaunchedEffect` для выполнения сторонних эффектов (например, API-запросов), то изменение в ответ на эти запросы вызывает рекомпозицию.
    
    ```kotlin
    LaunchedEffect(Unit) {
        // Perform some action
    }
    ```
    

### 7. **Изменение глобальных переменных или объектов (например, хранилища)**

- **Глобальные изменения или состояние в хранилище** (например, хранилища состояния, подобные `ViewModel` или `StateFlow`):  
    Когда данные из хранилища обновляются, компоненты, использующие эти данные, пересоздаются.

### 8. **Библиотечные компоненты (like `Text`, `Image`, etc.)**

- **Обновление входных параметров библиотечных компонентов**:  
    Если компоненты, такие как `Text`, `Image` или другие библиотеки, получают новые параметры, происходит рекомпозиция.

### 9. **Рекомпозиция для масштабирования (AnimatedContent, Transition, etc.)**

- **Animatable / Transition**:  
    Когда используется анимация или переходы (например, `AnimatedContent` или `Transition`), composable-функции перезапускаются, чтобы обновить UI с учетом новых состояний.

Таким образом, любое изменение, влияющее на входные параметры, состояния или системные события жизненного цикла, инициирует процесс рекомпозиции в Jetpack Compose.



В Jetpack Compose различают **стабильные** (`stable`) и **нестабильные** (`unstable`) параметры. Это важно для оптимизации производительности, так как нестабильные параметры могут вызывать лишние рекомпозиции.

### 1. **Стабильные параметры (`stable`)**

- **Что такое стабильные параметры?**:  
    Параметры, которые не изменяются после их первоначального назначения. Они не зависят от времени выполнения и остаются неизменными в течение всего жизненного цикла компонента.
- **Пример**:  
    Простой параметр, который передается в composable и не изменяется внутри компонента.
    
    ```kotlin
    @Composable
    fun Greeting(name: String) {
        Text("Hello, $name!")
    }
    ```
    
- **Преимущества**:  
    Стабильные параметры позволяют Compose оптимизировать перерисовку, так как компонент пересоздается только при их изменении.
- **Применение**:  
    Стабильные параметры должны использоваться для минимизации ненужных рекомпозиционных циклов.

---

### 2. **Нестабильные параметры (`unstable`)**

- **Что такое нестабильные параметры?**:  
    Параметры, которые могут изменяться во время выполнения или зависят от каких-либо событий, системных изменений или сторонних эффектов.
- **Пример**:  
    Параметр, который хранит текущее состояние или изменяется в зависимости от других объектов или API-запросов.
    
    ```kotlin
    @Composable
    fun Counter(counter: Int) {
        Button(onClick = { /* обновление состояния */ }) {
            Text("Counter: $counter")
        }
    }
    ```
    
- **Проблемы с нестабильными параметрами**:  
    Использование нестабильных параметров приводит к частым рекомпозициям, что может снизить производительность.
- **Когда использовать нестабильные параметры?**:  
    Нестабильные параметры могут быть необходимы, если компонент зависит от внешних источников данных, которые могут изменяться (например, состояния, потоковые данные, API-запросы).

---

### Как определить стабильные и нестабильные параметры?

1. **Определение стабильных параметров**:
    - Параметры, которые передаются через `remember` и не изменяются.
    - Простые значения, которые остаются неизменными.
    - Параметры с ключами (`key`) помогают определить стабильность.
2. **Определение нестабильных параметров**:
    - Состояния, изменяемые через `mutableStateOf`, `LiveData`, `Flow`, `StateFlow`, или другие асинхронные источники данных.
    - Параметры, которые зависят от внешних событий или жизненного цикла приложения.

---

### Влияние на производительность:

- **Использование стабильных параметров** улучшает производительность и помогает минимизировать избыточные рекомпозиции.
- **Использование нестабильных параметров** может привести к большому числу лишних обновлений UI, что снижает производительность.
