# Binder и AIDL

Обзор всех способов межпроцессного взаимодействия — в [[IPC. How two apps communicate]]. Здесь подробно про механизм, на котором держится **всё** остальное.

## Зачем Binder
Каждое приложение Android живёт в своём процессе с изолированной памятью, и почти любое системное действие — это вызов чужого процесса: `startActivity` идёт в `system_server`, получение сервиса — тоже. В Linux уже были средства IPC (сокеты, пайпы, shared memory), но их отвергли:
- **Двойное копирование**: обычно данные копируются из процесса-отправителя в ядро и оттуда в получателя.
- Нет встроенной **идентификации вызывающего** — приложение могло бы соврать, кто оно.
- Нет привязки к **жизненному циклу** и подсчёта ссылок.

**Binder** — драйвер ядра Linux, написанный специально под эти требования.

## Как он работает
1. Клиент упаковывает аргументы в **`Parcel`** (плоский буфер).
2. Вызывает `transact()` у **проксирующего** объекта.
3. Драйвер копирует данные **один раз** — сразу в отображённую (`mmap`) память процесса-получателя.
4. В получателе просыпается поток из **binder thread pool**, вызывается `onTransact()`, результат уходит обратно.
5. Клиентский поток всё это время **заблокирован** — вызов синхронный (если не помечен `oneway`).

Ключевые свойства, которые спрашивают:
- **Одно копирование** вместо двух — за счёт `mmap` разделяемого буфера.
- **Ядро подставляет UID/PID вызывающего** — `Binder.getCallingUid()` нельзя подделать, на этом стоит вся проверка разрешений в Android. См. [[Permissions]].
- **Подсчёт ссылок и `linkToDeath`**: можно узнать, что процесс на том конце умер.
- **Лимит транзакции ~1 МБ на процесс** — отсюда `TransactionTooLargeException`. См. [[Intent and Bundle data size limits]].
- Вызовы приходят из **пула потоков** (по умолчанию до 16), поэтому сервис обязан быть потокобезопасным. См. [[Multithreading]].

## AIDL
**AIDL** (Android Interface Definition Language) — язык описания интерфейса; по `.aidl`-файлу генерируется код маршалинга, чтобы не писать `Parcel` руками.

```aidl
// IRemoteService.aidl
interface IRemoteService {
    int add(int a, int b);
    oneway void log(String message);   // не ждать ответа
}
```
Из него генерируются две половины:
- **`Stub`** — абстрактный класс на стороне сервиса: принимает транзакцию, распаковывает аргументы, зовёт твою реализацию.
- **`Proxy`** — на стороне клиента: выглядит как обычный интерфейс, внутри пакует аргументы и делает `transact()`.

```kotlin
// сервис
class RemoteService : Service() {
    private val binder = object : IRemoteService.Stub() {
        override fun add(a: Int, b: Int) = a + b      // выполняется в binder-потоке!
        override fun log(message: String) { /* ... */ }
    }
    override fun onBind(intent: Intent) = binder
}

// клиент
val api = IRemoteService.Stub.asInterface(binder)
val sum = api.add(2, 3)      // выглядит как локальный вызов, внутри — транзакция
```

`asInterface` содержит важную оптимизацию: если объект оказался **в том же процессе**, возвращается прямая ссылка без всякого IPC.

### Направления параметров
В AIDL у непримитивных параметров обязательно указывают направление: `in` (передать), `out` (заполнить на той стороне), `inout` (оба). По умолчанию `in` — и это не формальность: `out`/`inout` требуют обратного копирования и дороже.

### oneway
Метод, помеченный `oneway`, возвращает управление сразу, не дожидаясь выполнения, и не может возвращать значение. Так избегают блокировки клиентского потока и **дедлоков** при взаимных вызовах.

## Что выбрать
| Механизм | Когда | Стоимость |
| --- | --- | --- |
| **Intent / BroadcastReceiver** | разовые события, запуск компонентов | просто, но медленно и без ответа |
| **ContentProvider** | структурированный доступ к данным по URI | готовая модель прав |
| **Messenger** | последовательная обработка сообщений между процессами | обёртка над Handler + Binder, один поток |
| **AIDL** | прямые вызовы методов, параллельные запросы | сложнее всего; нужен, когда важна скорость и конкурентность |

Правило: `Messenger` достаточно, пока запросы можно обрабатывать по очереди; AIDL берут, когда нужна параллельность.

## Грабли
- **Методы Stub выполняются не на главном потоке** — обращаться к UI напрямую нельзя, а общее состояние нужно синхронизировать.
- **Большие данные** через AIDL → `TransactionTooLargeException`. Передавай ссылку/URI, а данные — через `FileProvider`, `ContentProvider` или `ashmem`.
- **Синхронный вызов может подвесить UI** — вызовы с главного потока делать нельзя, либо помечать `oneway`.
- **Взаимные синхронные вызовы** двух процессов дают дедлок; спасает `oneway`.
- **`exported` сервис без проверки прав** — любой сможет вызывать твои методы; проверяй `checkCallingPermission()` или `Binder.getCallingUid()`.
- Изменение `.aidl` — это **изменение контракта**: клиент, собранный со старой версией, сломается.

## Вопросы-ловушки
- Почему в Android свой IPC, а не стандартные средства Linux? → одно копирование вместо двух, надёжная идентификация вызывающего, подсчёт ссылок и уведомление о смерти процесса.
- Сколько раз копируются данные при binder-транзакции? → один раз, в `mmap`-область получателя.
- На каком потоке выполняется метод AIDL-сервиса? → на потоке из binder thread pool, не на главном.
- Что делает `oneway`? → делает вызов асинхронным без возвращаемого значения; средство от блокировок и дедлоков.
- Можно ли доверять UID из аргументов? → нет, только `Binder.getCallingUid()` — его подставляет ядро.
- Что произойдёт при передаче 5 МБ через AIDL? → `TransactionTooLargeException`, лимит буфера ~1 МБ на процесс.
