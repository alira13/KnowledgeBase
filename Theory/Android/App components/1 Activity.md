# Activity

**Activity** — экран приложения: точка, где система отдаёт приложению окно, а пользователь взаимодействует с UI. Это один из четырёх основных компонентов Android (наряду с `Service`, `BroadcastReceiver`, `ContentProvider`), и, как все они, регистрируется в манифесте и создаётся **системой**, а не твоим кодом.

Ключевая мысль, из которой растут все вопросы на собеседовании: **Activity тебе не принадлежит**. Система вправе пересоздать её при повороте экрана и убить процесс целиком, когда не хватает памяти. Задача разработчика — пережить и то и другое.

При переходах между экранами экземпляры Activity складываются в **стек** (back stack), и положение в стеке задаёт состояние: активна (на переднем плане), приостановлена (видна частично), остановлена (не видна), уничтожена. Состояние определяет **системный приоритет процесса** — чем ниже, тем скорее процесс убьют при нехватке памяти. Подробно про стек, Task и `launchMode` — [[Navigation. BackStack]].

## Колбэки жизненного цикла

| Колбэк | Когда | Что здесь делать |
| --- | --- | --- |
| `onCreate(savedInstanceState)` | один раз при создании | `setContentView`, инициализация, восстановление состояния |
| `onStart()` | экран стал видимым | подписки, зависящие от видимости |
| `onResume()` | экран получил фокус, интерактивен | камера, сенсоры, анимации, старт воспроизведения |
| `onPause()` | теряет фокус (диалог, split-screen) | остановить то, что тратит батарею; **работает быстро** |
| `onStop()` | экран не виден | отписки, сохранение данных в БД |
| `onDestroy()` | уничтожение (finish или пересоздание) | освобождение ресурсов, обнуление ссылок |

`onPause()` не место для сохранения данных: он блокирует показ следующего экрана, и с Android 9 система не гарантирует вызова `onStop`/`onDestroy` до убийства процесса. Сохранять — в `onStop()` (на диск) и `onSaveInstanceState()` (в Bundle).

## Последовательности при типовых действиях
Это спрашивают почти всегда — важен именно порядок.

1. **Запуск**: `onCreate` → `onStart` → `onResume`.
2. **Кнопка «Домой»**: `onPause` → `onStop`. Activity **не уничтожается**. Возврат: `onRestart` → `onStart` → `onResume`.
3. **Переход на другой экран**: `onPause` (текущая) → `onCreate`/`onStart`/`onResume` (новая) → `onStop` (текущая). Обрати внимание: новая Activity стартует **до** того, как старая остановлена.
4. **Кнопка «Назад»**: `onPause` → `onStop` → `onDestroy`, экран снимается со стека и не восстанавливается.
5. **Поворот экрана**: `onPause` → `onSaveInstanceState` → `onStop` → `onDestroy` → `onCreate(savedInstanceState)` → `onStart` → `onRestoreInstanceState` → `onResume`.

Отличие пунктов 4 и 5 — ключевое: в обоих случаях вызывается `onDestroy`, но при повороте Activity **пересоздаётся**, а по кнопке «Назад» — уходит навсегда. Различить можно через `isFinishing` или `isChangingConfigurations`.

## Изменение конфигурации (config change)
**Конфигурация** — параметры окружения: ориентация, размер окна, язык, тема (день/ночь), плотность экрана, размер шрифта. При их изменении система **уничтожает и пересоздаёт** Activity, чтобы подтянуть подходящие ресурсы (`layout-land`, `values-ru`, `drawable-xxhdpi`).

Что переживает пересоздание:
- ✅ **ViewModel** — живёт до `onCleared()`, т.е. до реального завершения экрана. Основное место для состояния экрана. См. [[1 ViewModel, ViewModelProvider]].
- ✅ **`onSaveInstanceState` (Bundle)** — переживает и пересоздание, и смерть процесса, но ограничен по размеру (~500 КБ на всю транзакцию) и хранит только `Parcelable`/примитивы. См. [[Bundle]], [[Intent and Bundle data size limits]].
- ❌ **Поля Activity** — теряются.

Отдельный приём — `android:configChanges="orientation|screenSize|..."` в манифесте: тогда система не пересоздаёт Activity, а вызывает `onConfigurationChanged()`. Считается **плохой практикой** (кроме особых случаев вроде видеоплеера): ты берёшь на себя ручную перезагрузку всех ресурсов и легко получаешь неправильную вёрстку в ландшафте.

## Process death — то, что забывают
Когда приложение в фоне, система может убить **весь процесс** ради памяти. Пользователь возвращается — и видит не заново запущенное приложение, а восстановленный стек экранов: система пересоздаёт Activity и передаёт сохранённый `savedInstanceState`.

Разница, о которой спрашивают:

| | Поворот экрана | Process death |
| --- | --- | --- |
| ViewModel | ✅ выживает | ❌ теряется |
| `savedInstanceState` | ✅ выживает | ✅ выживает |
| Статические поля, синглтоны | ✅ | ❌ (процесс новый) |

Отсюда правило: в `SavedStateHandle`/`Bundle` кладут **минимум для восстановления** (id выбранного элемента, поисковый запрос, позиция скролла), а не сами данные — данные перезапрашивают из репозитория.

Проверять руками: свернуть приложение → в Logcat «Terminate application» (или `adb shell am kill <package>`) → вернуться из «Недавних». Опция разработчика «Не сохранять действия» (`Don't keep activities`) воспроизводит это же постоянно.

## Разметка
Связывание с UI — в `onCreate` через `setContentView()`:
```kotlin
class MainActivity : AppCompatActivity() {
    private lateinit var binding: ActivityMainBinding

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        binding = ActivityMainBinding.inflate(layoutInflater)
        setContentView(binding.root)          // View Binding вместо findViewById
        binding.textView.text = "Привет"
    }
}
```
Подробно про Binding и почему он лучше `findViewById` — [[1 View Binding]]. В Compose вместо этого `setContent { }`.

## Почему фрагменты — не основной компонент
Частый смежный вопрос. `Fragment` не регистрируется в манифесте, не может быть запущен системой и не существует вне хоста — он всегда живёт внутри Activity и подчинён её жизненному циклу. Это переиспользуемый кусок UI со своим жизненным циклом, а не самостоятельный компонент. См. [[2 Fragments]].

Современный подход — **Single Activity**: одна Activity, экраны — фрагменты или composable-функции. Это снимает почти всю боль с `launchMode`, `Task` и флагами `Intent`.

## Грабли
- **Утечка Activity**: сохранил `Context` активити в синглтоне/статике — после поворота старый экземпляр не соберётся GC. См. [[Context]], [[Memory leaks. Detection]].
- **Долгая работа в `onCreate`** — задержка первого кадра; тяжёлое уносим в фон.
- **Обращение к View после `onDestroyView`/`onDestroy`** — `NullPointerException` из отложенных колбэков; обнуляй `binding`.
- **`onSaveInstanceState` для больших данных** — `TransactionTooLargeException`.
- Не полагаться на `onDestroy` как на гарантированный колбэк: при убийстве процесса он не вызывается.

## Вопросы-ловушки
- Какие колбэки вызовутся при нажатии «Назад» на главном экране? → `onPause` → `onStop` → `onDestroy`; Activity не сохраняется в стеке.
- Чем поворот отличается от `finish()` с точки зрения кода? → и там и там `onDestroy`; различить помогает `isFinishing`/`isChangingConfigurations`, а ViewModel очищается только во втором случае.
- Переживёт ли ViewModel смерть процесса? → нет, только пересоздание Activity. Для process death нужен `SavedStateHandle`.
- Всегда ли вызывается `onDestroy`? → нет, система может убить процесс без него.
- Что делать, чтобы поворот не пересоздавал экран, и почему так лучше не делать? → `android:configChanges`; при этом ресурсы под новую конфигурацию не перезагрузятся автоматически.
