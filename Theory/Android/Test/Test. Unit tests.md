# Unit-тесты (JUnit)

**Unit-тест** проверяет один компонент в изоляции: класс, функцию, ViewModel. Живёт в `src/test/`, выполняется на JVM за миллисекунды. Общий контекст — [[Testing]].

## JUnit 4 и JUnit 5
| | JUnit 4 | JUnit 5 |
| --- | --- | --- |
| Подготовка/очистка | `@Before` / `@After` | `@BeforeEach` / `@AfterEach` |
| Один раз на класс | `@BeforeClass` (статический) | `@BeforeAll` |
| Расширения | `@Rule`, `@ClassRule` | `@ExtendWith` |
| Ожидание исключения | `@Test(expected = ...)` | `assertThrows { }` |
| Вложенные группы | нет | `@Nested` |
| Параметризация | отдельный runner | `@ParameterizedTest` |

В Android по умолчанию до сих пор JUnit 4 — на нём построены Espresso и правила вроде `InstantTaskExecutorRule`. JUnit 5 удобнее для чистых модулей (domain, data), но требует отдельного плагина. Инструментальные тесты — только JUnit 4.

## Структура теста
```kotlin
class CalculatorTest {

    private lateinit var calculator: Calculator

    @Before
    fun setUp() {
        calculator = Calculator()        // новый экземпляр на каждый тест
    }

    @Test
    fun `when multiply by zero then result is zero`() {
        val result = calculator.multiply(5.0, 0.0)

        assertEquals(0.0, result, DELTA)
    }
}
```
`@Before` выполняется **перед каждым** тестом — это и обеспечивает независимость: состояние не перетекает между тестами. Полагаться на порядок выполнения нельзя, он не гарантирован.

**Имя теста** — предложение в обратных кавычках, описывающее сценарий: `when <условие> then <ожидание>`. Из отчёта о падении сразу видно, что сломалось, без чтения кода.

## Assertions
```kotlin
assertEquals(expected, actual)          // порядок важен: сначала ожидаемое
assertTrue(list.isEmpty())
assertNull(result)
assertThrows<IllegalArgumentException> { parse("") }   // JUnit 5
```

**Дробные числа — только с погрешностью.** Двоичное представление `double` не хранит десятичные дроби точно, поэтому накопленная сумма не равна ожидаемой:
```kotlin
@Test
fun `when 0,01 multiply 100 then result equals 1 with delta`() {
    val actual = Calculator().multiply(0.01, 100.0)   // 1.0000000000000007, а не 1.0

    assertEquals(1.0, actual, 0.001)                   // delta обязательна
}
```
Без `delta` тест упадёт, хотя код верен. Там, где точность критична (деньги), используют `BigDecimal` или целые копейки, а не `double`.

Для читаемых сообщений о падении берут AssertK или Truth:
```kotlin
assertThat(user.name).isEqualTo("Alice")   // в отчёте видно оба значения
```

## Параметризованные тесты
Когда логика одна, а входных данных много:
```kotlin
@ParameterizedTest
@CsvSource("a@b.com, true", "a@, false", "'', false")
fun `email validation`(input: String, expected: Boolean) {
    assertEquals(expected, EmailValidator.isValid(input))
}
```
Лучше цикла внутри одного теста: каждый случай отображается отдельно, и падение указывает на конкретные данные.

## Что именно проверять
- **Краевые случаи**: пустая строка и список, `null`, ноль, отрицательные числа, максимум, дубликаты.
- **Ошибочные пути** — их забывают чаще всего: некорректный ввод, исключение из зависимости.
- **Поведение, а не реализацию**: результат и наблюдаемое состояние, а не то, какие приватные методы вызывались.

## Грабли
- **Общее изменяемое состояние** между тестами (поле без пересоздания в `@Before`, `object`, статика) — тесты начинают зависеть от порядка и «мигать».
- **Зависимость от времени**: `System.currentTimeMillis()`, `LocalDate.now()` делают тест недетерминированным. Внедряй `Clock` и подменяй фиксированным.
- **Логика в тесте**: `if`/циклы в проверке — источник ошибок в самом тесте, ожидаемое значение лучше писать константой.
- **Android-классы в JVM-тесте**: `Log.d` вернёт 0, а многое другое бросит «not mocked». Либо не тащить Android в тестируемый слой, либо Robolectric.
- **Один тест на всё** — при падении неясно, что именно сломалось.

## Вопросы-ловушки
- Почему `assertEquals(1.0, 0.01 * 100)` падает? → двоичное представление `double`, нужна `delta` или `BigDecimal`.
- Зачем `@Before`, если можно инициализировать поле сразу? → гарантия чистого состояния перед каждым тестом.
- Можно ли рассчитывать на порядок тестов? → нет, тесты обязаны быть независимыми.
- Чем `@ParameterizedTest` лучше цикла? → каждый случай виден отдельно и падает адресно.
- Почему в JVM-тесте падает код с `Log`? → в `test/` подставлена заглушка android.jar без реализации.
