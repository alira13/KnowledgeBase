# Тестовые двойники (fake, mock, stub)

Чтобы протестировать класс в изоляции, его зависимости подменяют — сетью ходить нельзя, база медленная, а поведение должно быть предсказуемым. Подменённая зависимость называется **тестовым двойником (test double)**.

Это работает только если зависимости **внедряются извне**, а не создаются внутри. Тестируемость — прямое следствие Dependency Injection. См. [[Dependency injection]].

## Пять видов
| Вид | Что делает | Пример |
| --- | --- | --- |
| **Dummy** | заглушка ради заполнения параметра, не используется | `Logger` в конструкторе, который тест не трогает |
| **Stub** | возвращает заранее заданные значения | репозиторий, всегда отдающий один список |
| **Fake** | **рабочая** упрощённая реализация | репозиторий на `MutableList` в памяти вместо БД |
| **Mock** | проверяет, **как** его вызывали | «метод `save()` вызван ровно один раз» |
| **Spy** | настоящий объект с частичной подменой | реальный сервис, у которого подменён один метод |

Различие mock и stub — любимый вопрос: **stub нужен, чтобы тест мог выполниться** (подаёт данные), **mock нужен, чтобы что-то проверить** (записывает вызовы и позволяет их верифицировать).

## Fake — обычно лучший выбор
```kotlin
class FakeUserRepository : UserRepository {
    private val users = mutableListOf<User>()
    var shouldFail = false                      // управляем сценарием ошибки

    override suspend fun getUsers(): Result<List<User>> =
        if (shouldFail) Result.Error(DataError.NETWORK) else Result.Success(users)

    override suspend fun save(user: User) { users += user }
}
```
Почему фейк чаще предпочтительнее мока:
- **Тест проверяет поведение, а не вызовы.** Сохранили пользователя → он есть в списке. Такой тест переживёт рефакторинг, а мок с `verify(repo.save(...))` — нет.
- **Один фейк переиспользуется** десятками тестов; настройка мока пишется в каждом заново.
- **Читаемость**: в тесте видно состояние, а не пять строк настройки заглушек.
- Фейк **компилируется** вместе с интерфейсом: изменил контракт — сразу видно, где чинить.

Цена — фейк надо написать и поддерживать. Для интерфейса из двух методов это минуты.

## Mockk — когда моки уместны
`mockk` — стандарт для Kotlin (в отличие от Mockito умеет final-классы, корутины, объекты).
```kotlin
val repo = mockk<UserRepository>()
coEvery { repo.getUsers() } returns Result.Success(listOf(user))   // stub

val viewModel = UsersViewModel(repo)
viewModel.load()

coVerify(exactly = 1) { repo.getUsers() }                          // mock-проверка
```
- `every` / `coEvery` — задать поведение (для `suspend` — версии с `co`).
- `verify` / `coVerify` — проверить факт вызова.
- `relaxed = true` — не падать на ненастроенных методах, возвращая значения по умолчанию.
- `mockk<T>(relaxUnitFun = true)` — то же только для функций, возвращающих `Unit`.

Моки оправданы, когда:
- зависимость **сторонняя и сложная** (Firebase, платёжный SDK) — писать фейк дорого;
- проверяемое поведение **и есть факт вызова**: «аналитика отправила событие», «токен обновлён ровно один раз»;
- нужно смоделировать редкое исключение.

## Чего избегать
- **Мокать то, что тестируешь.** Если половина тестируемого класса — spy, тест проверяет заглушку.
- **Мокать типы данных** (`data class`, `List`) — просто создай настоящий объект.
- **Проверять каждый вызов** (`verify` на всё подряд) — тест превращается в копию реализации и ломается при любом рефакторинге.
- **Мокать чужие интерфейсы напрямую** — лучше обернуть сторонний SDK своим интерфейсом и подменять его.

## Реальные зависимости в тестах
Иногда подменять не нужно:
- **Room** — есть in-memory база: настоящий SQL, но быстро и без файла.
- **Сеть** — `MockWebServer` от OkHttp: настоящий HTTP-клиент против локального сервера с заготовленными ответами. Проверяет ещё и парсинг, и заголовки.

Это уже интеграционные тесты, и они ценнее, чем мок вокруг DAO.

## Вопросы-ловушки
- Чем mock отличается от stub? → stub подаёт данные, чтобы тест прошёл; mock проверяет, как его вызывали.
- Почему fake обычно лучше мока? → тест проверяет поведение и результат, а не последовательность вызовов, и переживает рефакторинг.
- Почему `mockk`, а не Mockito? → Kotlin-классы по умолчанию `final`, а mockk умеет их, корутины и `object` из коробки.
- Что не так с `verify` на каждый вызов? → тест дублирует реализацию и ломается без изменения поведения.
- Как тестировать DAO? → in-memory Room, а не мок: проверяется настоящий SQL.
