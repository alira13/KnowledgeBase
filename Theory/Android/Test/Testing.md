# Тестирование — вход в тему

Тест — это код, который проверяет другой код и **падает, когда поведение сломалось**. Ценность не в самом факте наличия тестов, а в том, что они дают: возможность менять код без страха, документацию поведения и быструю обратную связь вместо ручного прокликивания.

На senior-собесе тестирование почти всегда отдельная секция. Спрашивают не «знаешь ли ты JUnit», а **что и на каком уровне ты тестируешь и почему**.

## Пирамида тестов
| Уровень | Что проверяет | Скорость | Где запускается | Сколько |
| --- | --- | --- | --- | --- |
| **Unit** | один класс в изоляции: ViewModel, use case, маппер, парсер | миллисекунды | JVM (`test/`) | большинство |
| **Integration** | несколько компонентов вместе: репозиторий + Room, DAO, сериализация | сотни мс | JVM или устройство | заметно меньше |
| **UI / E2E** | сценарий глазами пользователя | секунды и десятки секунд | эмулятор/устройство (`androidTest/`) | единицы, только критичные пути |

Форма пирамиды следует из цены: UI-тест на порядки медленнее unit-теста, чаще ломается по посторонним причинам и хуже локализует ошибку. Перевёрнутая пирамида («мороженое») — типичная беда: сборка идёт час, тесты периодически краснеют без причины, и им перестают верить.

## Что тестировать в каждом слое
- **Domain (use case, валидация)** — идеальный кандидат: чистый Kotlin, без Android. Тестируется тривиально и даёт максимум пользы.
- **Data (репозиторий, маппер, парсер)** — маппинг DTO → domain, обработка ошибок сети, кэш. Источники подменяются фейками.
- **Presentation (ViewModel)** — переходы состояний: действие пользователя → ожидаемый `State`. Проверяем `State`/`Event`, а не внутренние поля.
- **UI** — только сценарии: «открыл экран → вижу список», «нажал → перешёл».

Не тестируют: геттеры/сеттеры, `data class`, сторонние библиотеки, конфигурацию — это шум, который придётся править при каждом рефакторинге.

## Хороший тест
- **Быстрый** — иначе его перестанут гонять.
- **Независимый** — не зависит от порядка выполнения и других тестов; общее состояние сбрасывается.
- **Детерминированный** — не зависит от времени, сети, часового пояса, случайных чисел. Их подменяют (`Clock`, фиксированный seed).
- **Проверяет поведение, а не реализацию** — тест не должен падать после рефакторинга, не менявшего поведение. Это главный признак: тест, знающий про приватные детали, — обуза.
- **Понятен по имени падения** — из отчёта видно, что сломалось, без чтения кода.

## Структура: given / when / then
```kotlin
@Test
fun `when login with empty password then shows validation error`() {
    // given — исходное состояние
    val viewModel = LoginViewModel(FakeAuthRepository())

    // when — действие
    viewModel.onAction(LoginAction.Submit(email = "a@b.c", password = ""))

    // then — проверка
    assertEquals(LoginError.EmptyPassword, viewModel.state.value.error)
}
```
Имя теста на русском/английском в обратных кавычках — предложение, описывающее сценарий, а не `test1`. Одна проверка смысла на тест: если в `then` три несвязанные проверки, тестов должно быть три.

## Инструменты
| Задача | Чем |
| --- | --- |
| Запуск тестов | JUnit4 (`@Test`, `@Before`) или JUnit5 |
| Проверки | `assertEquals`, AssertK/Truth для читаемых сообщений |
| Подмена зависимостей | ручные фейки, mockk. См. [[Test. Test doubles]] |
| Корутины и Flow | `runTest`, `TestDispatcher`, Turbine. См. [[Test. Coroutines and Flow]] |
| UI | Espresso (View), `ComposeTestRule` (Compose). См. [[Test. UI]] |
| БД | Room in-memory база |
| Сеть | MockWebServer от OkHttp |

## Где лежат тесты
- `src/test/` — **unit**, выполняются на JVM, быстро. Android-классы здесь недоступны (`Log`, `Context` вернут заглушки или упадут) — либо не тащить их в тестируемый код, либо Robolectric.
- `src/androidTest/` — **инструментальные**, выполняются на устройстве/эмуляторе, есть настоящий `Context`.

Именно поэтому архитектура и тестируемость связаны: чем меньше Android в слоях domain и data, тем больше кода покрывается быстрыми JVM-тестами. См. [[Clean architecture]].

## Про покрытие
Покрытие (coverage) показывает, какие строки исполнились под тестами, — и только. 100% покрытия не означает корректности: тест без единой проверки тоже «покрывает» код. Полезно смотреть на **непокрытые** участки критичной логики, вредно — превращать процент в KPI.

## Вопросы-ловушки
- Почему UI-тестов должно быть мало? → они медленные, флакающие и плохо локализуют причину поломки.
- Что тестировать во ViewModel? → переходы состояний в ответ на действия, а не внутренние поля и вызовы.
- Тест упал после рефакторинга без изменения поведения — что это значит? → тест проверяет реализацию, а не поведение; его нужно переписать.
- Зачем разделение `test/` и `androidTest/`? → первые идут на JVM за миллисекунды, вторым нужен настоящий Android-рантайм.
- Гарантирует ли 100% покрытие отсутствие багов? → нет, покрытие измеряет исполнение строк, а не проверки.
