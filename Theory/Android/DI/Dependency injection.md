**DI** (Dependency Injection) — это **паттерн проектирования**, который используется для управления зависимостями между объектами. В контексте разработки программного обеспечения, особенно в мобильной и серверной разработке, DI помогает сделать код более **модульным**, **тестируемым** и **масштабируемым**

Dependency Injection — это способ **передачи** зависимостей объекту, вместо того чтобы объект сам их создавал. DI позволяет инжектировать зависимости в объект через конструктор, метод или поле.



**Внедрение зависимостей** (Dependency Injection) — это процесс предоставления внешней зависимости программному компоненту. Например, мы хотим предоставить зависимость `ViewModel` в `Activity`.

Некоторая логика, которая создает объекты и передает зависимости от одного объекта другому  
  

Проблема:

В простом случае для небольшого проекта обычно создается Creator, который создает зависимости. Но для большого проекта он очень сильно разрастется, плюс некоторые зависимости должны быть синглтоном, а в другом случае они же не должны быть. Нужно как-то разбираться с жизненным циклом. Поэтому появились инструменты DI

  

Преимущества DI:

- Мы повышаем независимость классов и обеспечиваем возможность повторного использования кода
- Упрощаем поддержку классов, так как избавляемся от нужды явно поддерживать зависимые классы и следить за изменениями в них.

- _Пример внедрения зависимостей без фреймворков:_
    
    _У нас есть класс компьютера_ _`Computer`__, и он использует для отображения класс_ _`Display`__. Класс_ _`Display`_ _представляет зависимость, а класс_ _`Computer`_ _зависит от класса_ _`Display`__._  
      
    Варианты получить экземпляр класса  
    `Display`
    
    1. Класс создаёт необходимую зависимость самостоятельно - НЕ внедрение зависимостей, так как класс сам создает экземпляр класса. При желании заменить Display придется менять весь класс
        
        ```Kotlin
        class Computer {
        	private val display = Display()
        	
        	fun show() {
        	    display.show()
        	}
        }
        
        fun main(args: Array) {
        	val computer = Computer()
        	computer.show()
        }
        
        class Display
        ```
        
        1. Самый простой способ внедрения - предоставить зависимость в качестве параметра конструктора или передать их в функции. Класс не создает экземпляр класса, а принимает как зависимость извне
            
            ```Kotlin
            class Computer(private val display: Display) {
            	fun show() {
            		display.show()
            	}
            }
            
            fun main(args: Array) {
            	val display = Display()
            	val computer = Computer(display)
            	computer.show()
            }
            
            class Display
            ```
            
            1. Передать зависимость через поле. Поле должно быть изменяемым, не лучший подход.
                
                ```Kotlin
                class Computer {
                	var display: Display? = null
                	
                	fun show() {
                        display?.show()
                  }
                }
                
                fun main(args:Array){
                	 val computer = Computer()
                	 computer.display = Display()
                	 computer.show()
                }
                ```
                
- Недостатки жизнь без фреймворков:
    - Например, если нужно, чтобы какой-то класс работал, пока живёт `Activity`, придётся изобретать подход, чтобы какие-то классы пересоздавались, а какие-то создавались один раз.
    - Затем может понадобиться организовать классы в блок, чтобы для набора классов жизненный цикл был одинаковый. Например, классы конкретного экрана, а при выходе с него мы хотим, чтобы ненужные классы очистились, чтобы не занимать лишнюю память.
    - Также мы хотим следовать принципу инверсии зависимостей, поэтому нужно, чтобы реализация какого-либо интерфейса была надёжно скрыта от других частей кода.
    - Дальше к нам на проект начнут приходить новые ребята и нужно будет унифицировать всю работу с DI, чтобы никто не изобретал велосипед.  
        Иначе мы в проекте изобретём DI-фреймворк. Это возможный, но часто ненужный путь.  
        

  

**DI-фреймворки**

Преимущества DI-фреймворков:

- + Различные функции для гибкой настройки жизненного цикла зависимостей.
- + Единый подход для чистоты кода.
- + Возможность легче проследить цепочки зависимостей между классами, что облегчает вхождение в проект для новичков, а также помогает ориентироваться в будущем.

Лучше определиться с фреймворком заранее, так как в проекте оставляют следы

  

**Статические**

для больших проектов и команд

**Dagger**, **Hilt**
- вся настройка передачи зависимостей происходит во время компиляции проекта.
- активно применяются механизмы кодогенерации: часть кода пишется не человеком, а создаётся библиотекой

**Преимущества**
- раннее выявление ошибок в настройке. Если мы где-то что-то не дописали, то поймём это на этапе компиляции проекта, ведь он просто не соберётся.

**Недостатки**
- Увеличивается время сборки. Для обеспечения безопасности требуется написание или же генерация дополнительного кода, что требует большего времени на этапе компиляции.
- Затрудняется поиск ошибок. В таких фреймворках используются особые аннотации для генерации кода, и часть кода создаётся библиотекой. Поэтому не всегда понятно, где человек допустил ошибку и как её быстро решить.

**Динамические**
для маленьких проектов и команд

**Koin**
- зависимости настраиваются во время работы программы

**Преимущества**
- Несложная настройка. Обычно описать создание зависимостей в динамическом фреймворке проще и быстрее, чем в статическом.
- Быстрая компиляция. Здесь не происходит дополнительного создания кода, поэтому проект компилируется быстрее.

**Недостатки**
- нет гарантии, что нужная зависимость есть в графе после компиляции. Мы узнаем, что допустили ошибку только во время работы программы, когда код запросит ту или иную зависимость
