# Линейный поиск — O(n)

**Линейный (последовательный) поиск** — простейший алгоритм поиска: идём по коллекции слева направо и сравниваем каждый элемент с искомым. Совпало — вернули результат, дошли до конца — элемента нет.

```kotlin
fun <T> linearSearch(list: List<T>, target: T): Int {
    for (i in list.indices) {
        if (list[i] == target) return i    // нашли — выходим сразу
    }
    return -1                              // не нашли
}
```

## Сложность
| Случай | Сравнений | Сложность |
| --- | --- | --- |
| Лучший — элемент первый | 1 | **O(1)** |
| Средний — элемент где-то в середине | n/2 | **O(n)** |
| Худший — элемент последний или отсутствует | n | **O(n)** |

Память — **O(1)**: дополнительных структур не нужно. См. [[Algorithm complexity]].

Константы отбрасываются, поэтому n/2 в среднем случае — это всё равно O(n): при удвоении данных время удваивается.

## Когда он уместен
Несмотря на «плохую» сложность, линейный поиск часто оптимален:
- **Данные не отсортированы.** Отсортировать ради одного поиска — O(n log n), то есть дороже самого поиска.
- **Коллекция маленькая** (десятки элементов). На малых n накладные расходы бинарного поиска и хеширования не окупаются.
- **Структура не даёт произвольного доступа** — например, связный список: там бинарный поиск невозможен в принципе, потому что нельзя за O(1) прыгнуть в середину. См. [[3. Non-linear. Linked list]].
- **Ищем по условию, а не по ключу**: «первый элемент дороже 100» — это `find { }`, тот же линейный поиск.

В Kotlin это `list.indexOf(x)`, `list.contains(x)`, `list.find { }`, `list.first { }` — все линейные.

## С чем сравнивать
| Способ | Требование | Сложность |
| --- | --- | --- |
| Линейный поиск | ничего | O(n) |
| Бинарный поиск | **отсортированные** данные + доступ по индексу | O(log n). См. [[Binary search O(log n)]] |
| Хеш-таблица (`HashSet`/`HashMap`) | хорошая хеш-функция, доп. память | O(1) в среднем. См. [[Collections. Overview]] |
| Дерево поиска (`TreeMap`) | сравнимые ключи | O(log n) + упорядоченность |

Практическое правило: **один поиск** по неотсортированным данным — линейный; **много поисков** — сначала построй индекс (`Set`/`Map`) за O(n), дальше каждый поиск O(1).

## Типичная ошибка в коде
Линейный поиск внутри цикла превращает O(n) в **O(n²)** — самая частая причина «почему список тормозит»:
```kotlin
// плохо: contains по списку внутри цикла → O(n * m)
for (item in items) {
    if (blockedList.contains(item.id)) continue
}

// хорошо: один раз построили Set → O(n + m)
val blocked = blockedList.toHashSet()
for (item in items) {
    if (item.id in blocked) continue
}
```

## Вопросы-ловушки
- Можно ли ускорить линейный поиск сортировкой? → для одного поиска нет: сортировка O(n log n) дороже; для многих — да.
- Почему в связном списке нельзя применить бинарный поиск? → нет доступа по индексу за O(1), переход к середине сам по себе O(n).
- Сложность в лучшем случае? → O(1), если искомое стоит первым; это не меняет оценку алгоритма, которую дают по худшему случаю.
