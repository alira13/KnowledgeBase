# Бинарный поиск — O(log n)

**Бинарный поиск** ищет элемент в **отсортированном** массиве, каждый раз отбрасывая половину оставшихся кандидатов. Возвращает позицию элемента или признак отсутствия.

Два обязательных условия: данные **отсортированы** и есть **доступ по индексу за O(1)**. Поэтому он работает с массивом и `ArrayList`, но не со связным списком.

## Принцип
1. Взять средний элемент отрезка.
2. Сравнить с искомым: совпало — ответ найден.
3. Искомое меньше — продолжить в левой половине, больше — в правой.
4. Повторять, пока отрезок не опустеет.

```
Ищем 7 в [1, 3, 5, 7, 9, 11, 13]
  середина 7 → нашли за 1 шаг

Ищем 3:
  [1,3,5,7,9,11,13] середина 7, 3 < 7 → влево
  [1,3,5]           середина 3 → нашли
```

## Реализация
```kotlin
fun binarySearch(arr: IntArray, target: Int): Int {
    var low = 0
    var high = arr.size - 1          // включительно

    while (low <= high) {
        val mid = low + (high - low) / 2      // защита от переполнения
        when {
            arr[mid] == target -> return mid
            arr[mid] < target -> low = mid + 1
            else -> high = mid - 1
        }
    }
    return -1                        // не найден
}
```
Рекурсивный вариант выглядит короче, но занимает O(log n) стека вместо O(1):
```kotlin
fun binarySearch(arr: IntArray, target: Int, low: Int = 0, high: Int = arr.size - 1): Int {
    if (low > high) return -1
    val mid = low + (high - low) / 2
    return when {
        arr[mid] == target -> mid
        arr[mid] < target -> binarySearch(arr, target, mid + 1, high)
        else -> binarySearch(arr, target, low, mid - 1)
    }
}
```

## Почему O(log n)
После каждого шага остаётся вдвое меньше элементов: n → n/2 → n/4 → … → 1. Число шагов k находится из n / 2ᵏ = 1, то есть **k = log₂ n**.

Практический смысл: в массиве из **миллиона** элементов ответ находится максимум за **20** сравнений, в миллиарде — за 30. Удвоение данных добавляет **один** шаг.

| | Значение |
| --- | --- |
| Время (худший/средний) | O(log n) |
| Время (лучший) | O(1) — попали в середину сразу |
| Память | O(1) итеративно, O(log n) рекурсивно |
| Предусловие | отсортированный массив с произвольным доступом |

## Три классические ошибки
1. **Переполнение** в `(low + high) / 2` — на больших индексах сумма выходит за `Int`. Пишут `low + (high - low) / 2`. Эта ошибка десять лет жила в JDK.
2. **Границы и зацикливание.** Смешение полуинтервала и отрезка: если писать `low = mid` вместо `low = mid + 1`, при двух оставшихся элементах `mid` перестаёт двигаться и цикл виснет. Держись одного соглашения: `high = size - 1` + `while (low <= high)` + `mid ± 1`.
3. **Данные не отсортированы** — алгоритм не упадёт, а вернёт мусор, и баг всплывёт далеко от места ошибки.

## В стандартной библиотеке
```kotlin
val index = list.binarySearch(target)         // список должен быть отсортирован
```
Возвращаемое значение стоит запомнить: если элемент **не найден**, возвращается `-(точка вставки) - 1` — отрицательное число, из которого можно получить позицию, куда элемент следовало бы вставить:
```kotlin
val i = list.binarySearch(x)
val insertionPoint = if (i >= 0) i else -i - 1
```

## Что ещё умеет бинарный поиск
- **Первое/последнее вхождение** при дубликатах: не выходить при совпадении, а продолжать сужать интервал в нужную сторону (`lowerBound`/`upperBound`).
- **Бинарный поиск по ответу** — приём для задач вида «найти минимальное X, при котором условие выполняется»: если условие монотонно (при большем X всё ещё верно), поиск идёт не по массиву, а по диапазону значений. Так решают «минимальная скорость», «минимальный размер» и подобные задачи.
- **Поиск в отсортированном сдвинутом массиве** — популярная задача LeetCode: одна из половин всегда отсортирована, по ней и определяют направление.

## Когда он не нужен
- Одиночный поиск в неотсортированных данных — дешевле линейный: сортировка стоит O(n log n). См. [[Linear search O(n)]].
- Частые поиски по ключу — выгоднее `HashMap`/`HashSet` с O(1). Бинарный поиск выигрывает, когда нужны ещё и **диапазоны** и **порядок**.
- Данные часто меняются — поддерживать массив отсортированным дорого; здесь уместнее дерево. См. [[Trees. Binary search tree]].

## Вопросы-ловушки
- Сколько шагов нужно для миллиона элементов? → около 20 (log₂ 10⁶).
- Почему `(low + high) / 2` — плохо? → переполнение `Int` при больших индексах.
- Что вернёт `binarySearch`, если элемента нет? → `-(insertion point) - 1`, а не просто −1.
- Можно ли применить к связному списку? → нет: переход к середине стоит O(n), выгода теряется.
- Как найти первое вхождение дубликата? → не останавливаться на совпадении, а сдвигать правую границу и запоминать кандидата.
