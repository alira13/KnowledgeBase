# Архитектурный собес: разборы типовых задач

Четыре задачи, которые дают чаще всего. Каркас ответа и чеклист вопросов — в [[Mobile app system design]]; здесь то, что специфично для каждой.

Общий приём: у каждой задачи есть **одно-два узких места**, ради которых её и дают. Интервьюер ждёт, что ты их найдёшь и разберёшь, а не распишешь все слои поровну.

---

## 1. Лента с оффлайном (соцсеть, новости)
**Узкое место:** пагинация + кэш + актуальность данных.

**Данные.** SSOT — база. Сеть пишет в неё, UI подписан на `Flow` из DAO. Пагинация — Paging 3 с `RemoteMediator`: он подгружает страницу из сети и складывает в Room, а `PagingSource` читает из базы. См. [[Paging 3]].

**Ключевые вопросы, которые нужно поднять самому:**
- **Инвалидация**: когда считать кэш устаревшим? Обычно TTL на запись (`cachedAt`) плюс pull-to-refresh. Полная очистка при refresh vs слияние — от этого зависит, «прыгнет» ли лента под пальцем.
- **Позиция скролла** при обновлении: вставка новых элементов сверху не должна дёргать экран — отсюда «показать N новых постов» кнопкой вместо автоподстановки.
- **Медиа**: картинки не в базе, а в файловом кэше (Coil/Glide), в БД только URL.
- **Размер базы**: лента бесконечная — нужна политика вытеснения (хранить N последних страниц).

**Оптимистичные действия.** Лайк должен отрабатывать мгновенно: пишем в БД сразу, запрос уходит фоном, при ошибке откатываем и показываем сообщение. Это отдельный пункт, который любят спрашивать.

## 2. Чат (real-time)
**Узкое место:** доставка сообщений и порядок при нестабильной сети.

**Транспорт.** WebSocket для активного чата, FCM для доставки, когда приложение закрыто. Сокет живёт, пока экран виден: подписка в `repeatOnLifecycle(STARTED)`, переподключение с экспоненциальной задержкой. См. [[Websocket]].

**Отправка сообщения.** Сообщение появляется в UI **до** ответа сервера — со статусом «отправляется». Механика:
1. Записать в БД со статусом `PENDING` и локальным id.
2. Отправить; при успехе — заменить на серверный id и статус `SENT`.
3. При ошибке — статус `FAILED` и кнопка «повторить».
4. Отправку недоставленных при возврате сети берёт на себя WorkManager.

Отсюда важная деталь: **локальный id и серверный id — разные вещи**, и модель должна это учитывать, иначе после переотправки появятся дубликаты.

**Порядок и дедупликация.** Сортировка по времени сервера, а не устройства (часы на телефоне врут). Дубликаты отсекаются по идемпотентному ключу, который генерирует клиент.

**История.** Пагинация «вверх» от последнего сообщения, храним последние N в базе, остальное подгружаем.

## 3. Загрузка и шеринг файлов (фото, документы)
**Узкое место:** долгая операция, переживающая закрытие экрана.

**Главное решение:** загрузка живёт **не в ViewModel**, а в `WorkManager` — иначе она умрёт вместе с экраном. Если пользователь должен видеть прогресс постоянно — foreground service с уведомлением. См. [[2 Services and WorkManager]].

**Что проговорить:**
- **Очередь и повторы**: `Constraints` (только Wi-Fi, не при низком заряде), backoff при ошибках.
- **Большие файлы**: chunked upload с возможностью продолжить, а не начинать заново.
- **Доступ к файлу**: Scoped Storage, `content://` URI и `takePersistableUriPermission` — путь к файлу может стать невалидным. См. [[2 External storage]].
- **Сжатие** до загрузки — экономия трафика; делать в фоне, не на главном потоке.
- **Прогресс** — из Worker через `setProgress`, UI подписан на `WorkInfo`.

## 4. Приложение с картой и геолокацией
**Узкое место:** батарея и разрешения.

**Разрешения** — полноценный сценарий, а не деталь: `ACCESS_COARSE`/`FINE_LOCATION`, отдельно фоновая геолокация (её Google проверяет вручную), объяснение пользователю зачем, поведение при отказе. См. [[Permissions]].

**Батарея.** Частота обновления координат — главный компромисс: `PRIORITY_HIGH_ACCURACY` в навигации, но `BALANCED` в фоне; останавливать подписку, когда экран не виден.

**Данные.** Кластеризация маркеров на клиенте при большом количестве точек, загрузка объектов по видимой области (bounding box) с дебаунсом при движении карты, кэш тайлов и объектов для оффлайна.

**Фон.** Трекинг маршрута — только foreground service с уведомлением; с Android 14 нужен `foregroundServiceType="location"` и соответствующее разрешение.

## Что оценивают во всех четырёх
| Что проверяют | Как это выглядит в ответе |
| --- | --- |
| Выясняешь ли требования | вопросы про объём, оффлайн, real-time до начала проектирования |
| Видишь ли узкое место | сам поднимаешь тему конфликтов, дубликатов, батареи |
| Знаешь ли платформенные ограничения | фоновые лимиты, Scoped Storage, разрешения по версиям |
| Думаешь ли о сбоях | нет сети, процесс убит, ошибка на середине операции |
| Умеешь ли выбирать | называешь альтернативу и цену выбора |
| Помнишь ли про эксплуатацию | аналитика, крэши, feature flag на новую фичу |

## Универсальные краевые случаи
Их стоит держать в голове для любой задачи:
- **Нет сети** в начале и **обрыв в середине** операции.
- **Process death** во время долгого действия. См. [[1 Activity]].
- **Поворот экрана** и другие изменения конфигурации.
- **Пустое состояние**, состояние ошибки, состояние загрузки — три экрана, про которые забывают.
- **Дубликаты** от повторной отправки.
- **Часы устройства** не совпадают с серверными.
- **Многоаккаунтность** и выход из аккаунта: что чистим в базе.
