# Чистая архитектура (Clean Architecture)

**Цель** — снизить связанность (coupling) и повысить тестируемость, разделив код на **слои** с чётким **правилом зависимостей**. Бизнес-логика не должна зависеть от UI, БД, фреймворков — их можно менять, не трогая ядро.

## Слои (снаружи внутрь)
- **Presentation** — UI и логика экрана: Compose/View + ViewModel (MVI/MVVM). Отображает состояние, ловит действия пользователя. Знает про Android.
- **Domain** — ядро: бизнес-правила. Содержит **доменные модели** (чистые сущности) и **use cases** (интеракторы) — одно действие = один класс (`GetRecipesUseCase`). Не зависит **ни от чего** (чистый Kotlin, без Android/Retrofit/Room). Идеально переносится в KMP.
- **Data** — реализация доступа к данным: **репозитории**, источники данных (remote/local), DTO, мапперы DTO↔domain. Знает про Retrofit/Room/DataStore.

## Правило зависимостей (главное!)
Зависимости направлены **внутрь, к Domain**. Внешние слои знают о внутренних, но **не наоборот**:
```
Presentation ──▶ Domain ◀── Data
```
Domain — в центре и **ни на кого не ссылается**. Как это возможно, если Data исполняет работу для Domain? Через **Dependency Inversion**: интерфейс репозитория объявлен в **domain**, а реализация — в **data**. Domain зависит от абстракции, которую сам же и диктует. См. [[OOP, SOLID, KISS, DRY, YAGNI, GRASP]] (принцип D в SOLID).

## Поток данных (пример «список рецептов»)
```
UI (Compose) → ViewModel → GetRecipesUseCase → RecipeRepository(интерфейс, domain)
                                                      ▲
                                          RecipeRepositoryImpl (data)
                                          ├─ RecipeApi (remote)
                                          └─ RecipeDao (local, SSOT)
```
Наверх возвращаются **доменные модели**, в UI — **UI-модели**. На каждой границе — маппинг, чтобы слои не протекали друг в друга.

## Зачем (что отвечать на собесе)
- **Тестируемость**: use cases и репозитории за интерфейсами → легко подменить фейком. См. [[Testing]].
- **Заменяемость**: сменить Retrofit на Ktor или Room на другую БД — правки только в data.
- **Независимость от фреймворка**: домен не «прибит» к Android.
- **Разделение ответственности**: тонкий UI, логика — в домене.

## Минусы / когда не нужно
- Много boilerplate (интерфейсы, мапперы, use cases) — для маленького приложения избыточно.
- Не каждому экрану нужен отдельный use case (иногда ViewModel → repository напрямую — прагматично).
