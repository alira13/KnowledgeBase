# Backend-Driven UI (BDUI)

Подход, при котором **сервер описывает структуру и содержимое экрана** (список компонентов, их порядок, данные, иногда стили и действия), а клиент лишь **рендерит** это описание готовым набором нативных компонентов.

## Идея
Сервер отдаёт не только данные, но и «вёрстку» экрана — обычно JSON вида «список блоков»:
```json
{ "screen": [
  { "type": "banner", "image": "...", "action": "deeplink://promo" },
  { "type": "product_carousel", "items": [ ... ] },
  { "type": "button", "title": "Купить", "action": "..." }
]}
```
Клиент имеет реестр: `type → Composable/View`. Неизвестные типы пропускает.

## Зачем (плюсы)
- **Изменения без релиза**: переставить блоки, поменять акцию, A/B-тесты, промо — правкой на сервере. Не ждём ревью в сторах.
- **Консистентность** между платформами (общий контракт).
- Быстрая кастомизация под сегменты пользователей.

## Минусы / риски
- Клиент должен уметь рендерить **все** типы блоков — новый тип всё равно требует релиза.
- Сложнее оффлайн, кэширование, тестирование, версионирование контракта.
- Труднее контролировать UX/производительность; легко «уплыть» в переусложнение.
- Обязательна обратная совместимость и graceful degradation для старых версий приложения.

## Где применяют
Витрины, ленты, главные экраны маркетплейсов и супераппов (Ozon, Avito, банки), где контент часто меняется. Экраны со сложной локальной логикой (формы, редакторы) обычно оставляют нативными.
